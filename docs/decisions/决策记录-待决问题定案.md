## 2. D1 命名与包名

**结论**：对外名称、PyPI 包名、GitHub 仓库名、brew formula 统一为 `skill-mcp-studio`。

**理由**：该名称已贯穿全部文档与现有 Codeup 仓库；「studio」贴合产品定位（多客户端工作台），与上游 `skills-mcp-unifier`（引擎）形成清晰分工——unifier 是底座，studio 是产品壳。

**落地动作**：阶段二打包时，`pyproject.toml` 的 `name`、`project.scripts` 入口、发布物命名全部对齐 `skill-mcp-studio`。

## 3. D2 许可证 = MIT

**结论**：采用 **MIT**。

**理由**：工具类项目、社区复用门槛最低、无专利条款维护负担；与上游生态（架构图技能即 MIT 来源）及 `skills-mcp-unifier` 的宽松传统一致；对下游（企业直接依赖）最友好。

**落地动作**：
1. 公开仓库根目录添加标准 `LICENSE`（MIT 文本），版权行留团队/组织填充；
2. `pyproject.toml` 声明 `license = "MIT"`；
3. SKILL.md / README 显著处标注许可证；
4. 阶段一在 Codeup 私有仓库即可先放 LICENSE 占位，公开时生效。

## 4. D3 仓库公开策略

**结论**：阶段一、二在 Codeup 私有仓库开发；**M1 达成「主干零个人拓扑」后**，公开到 GitHub，并同步上架 PyPI + homebrew tap。

**理由**：过早公开会把仍散布在 core/scripts/deploy 与**历史提交**中的个人拓扑（域名、内网网段、设备名）暴露出去；零个人拓扑是公开的硬前置条件，而非并列选择。

**落地动作**：
1. 公开前置检查（新增到 M2 发布 checklist）：
   - 主干代码（含 `git log` 历史）全文检索无个人域名/网段/设备名；含历史的仓库用 `git filter-repo` 或 squash 重建，必要时开新仓库导出版；
   - 测试夹具、README、SKILL.md 无个人拓扑残留；
2. 公开动作：GitHub 建仓 → PyPI 发布 `skill-mcp-studio` → homebrew tap；
3. 公开即标志着 v1.0（对应《产品形态与开发计划》§12 发布策略）。

## 5. D4 profile 分发形态 = 独立仓库 + 声明式引用

**结论**：真实 profile（含个人拓扑的 hermes-home）放入**独立仓库**；主仓库通过 `profile_sources` 声明式引用；主仓库 `profiles/` 仅保留无敏感的通用示例（`examples/generic-http`）。

**理由**：公开主仓库与个人拓扑在物理上分离，是最干净、不依赖「剥离」技巧的零泄漏方案；独立仓库也可设私有权限，天然控制可见范围。

**落地动作（含对阶段一第 4 步目录落点的修订）**：
1. 阶段一第 4(a) 步的「迁移到主仓库 `profiles/hermes-home/`」修订为「迁入独立仓库（建议私有）`profiles-hermes-home`」；
2. `config.yaml` 新增 `profile_sources` 段，支持两类 source：

```yaml
profile_sources:
  - git: git@codeup.example.com:acme/profiles-hermes-home.git
    ref: main
    path: profiles/hermes-home      # 仓库内相对路径
  - path: ~/.config/skill-mcp-studio/profiles   # 本地目录兜底
```

3. `profile_loader` 加载时先把 `profile_sources` 挂载/缓存到本地，再合并进可检索的 profiles 集合；加载失败 fail fast 并指明 source；
4. 主仓库 `profiles/examples/generic-http` 作为「无能力组」的最小示例入主仓库，供陌生人上手与测试。

## 6. D5 profile schema 版本化

**结论**：从 v1 起引入 `schema_version: 1`。

**理由**：profiles 段结构在阶段二起必然演进（已新增 `templates`、stdio 的 `command`/`args`）；版本字段是唯一能让「旧配置在升级后给出明确迁移提示」的抓手，成本极低，收益随时间放大。

**落地动作**：
1. config 顶层加 `schema_version: 1`（与 `profiles:` 平级）；`profile_loader._validate_schema_version` 校验：缺失视为 v1（legacy 兼容），未知版本 fail fast 并给出升级指引（退出码 2）；
2. 与阶段二汇总报告 JSON 的 `schema_version: 1` 对齐（阶段二详细设计 §4.3/§14.4）。

## 11. 阶段四收尾定案

### D11 技能清单语义 = 「仓库内非点子目录即技能」（定案，不改实现）

**背景**：阶段四启停（L5）以 `repo_skill_names()` 为唯一启停候选来源。仓库 175 个非点目录里既有真技能，也有 `_core`/`bin`/`scripts`/`mcp` 等基础设施目录，需定案「什么算技能」。

**实测（2026-09-04）**：`~/.skills-manager/skills` 下 175 个非点子目录，**175/175 全部带规范 `SKILL.md`**（含 `_core`/`bin`/`scripts`/`mcp`，均带 title/summary frontmatter，属仓库有意打包的可发现条目）。

**定案**：维持现状——「非点子目录即技能」（ADR-17 §4.1 口径），**不按 `SKILL.md` 二次过滤**。理由：

1. **无物可滤**：实测 175/175 均含 `SKILL.md`，过滤不改变清单，徒增一次全仓文件读；
2. **双层一致**：L2 `_all_entries_point_to_unified` 与 L5 清单同源（非点目录），过滤会制造 L2/L5 口径漂移；
3. **点规则即边界**：隐藏/系统条目（`.system`、`.git` 等）已由点前缀规则统一排除（阶段四收尾第 6/7 项修复），无需第二套判定；
4. **语义诚实**：`skills_total=175` 即「统一管理的仓库条目」，与客户端经根/逐技能链接实际可见的目录一致。

若未来仓库出现无 `SKILL.md` 的非点目录且确需排除，再按本条反案重开，不在本阶段预埋开关。

### D13 运行时禁用生效评估（定案：配置层即 DoD，运行时验证延后）

**问题**：`--disable-skill` 后，「禁用是否真从会话消失」要不要验证？

**已做到的（配置层，本工具边界内）**：
- L5 审计通道 2「禁用生效验证」：`verify_disable_effective` 逐技能核实无残留链接（原生禁用项豁免，见第 7 项）；
- 真实端到端证据链（收尾第 6 项）：Codex 禁用 `ascii-art` → 链接消失 → 审计精确漂移定位 → 启用还原 → 三关全绿；
- 各目标客户端均在会话启动时读取 skills 目录，符号链接移除对**新会话**结构性生效。

**为何运行时验证延后（证据）**：
1. **生态无人做到**：[Claude Code issue #36868](https://github.com/anthropics/claude-code/issues/36868)（bug / has repro / macOS / area:mcp）显示连 Anthropic 自己的原生禁用都会泄漏——Desktop 偏好里禁用的 SDK 型 MCP server 仍被注入每个会话的 `--mcp-config`（8 会话产生 523 个多余进程）；该 issue 2026-05-27 以 `not_planned`（stale bot）关闭，未见修复。配置层真相已是外部可保证的最强层面；
2. **无探测面**：没有任何目标客户端暴露「当前会话可见技能集」的可查询 API，外部验证无入口；
3. **机制无缓存风险**：本工具的禁用=移除符号链接，属客户端启动时必读的文件系统真相，不存在 #36868 式的「配置已禁但运行时仍注入」路径。

**定案**：运行时生效验证**不作为本工具 DoD**，无限期延后。**重开触发条件**（任一满足即重启评估）：
- 任一目标客户端暴露可查询的运行时技能/工具集 API；
- 出现某客户端运行期缓存 skills 目录、使符号链接真相失效的证据；
- #36868 类泄漏模式被证实波及 skills 目录（而非仅 MCP 配置）。

**D13 重开评估（2026-09-05，用户要求复核）**：逐客户端核查「可查询运行时
技能集」触发条件是否已满足：

| 客户端 | 运行时查询面（2026-09-05 调查） | 触发？ |
|--------|--------------------------------|--------|
| Claude Code | 2.1.261 新增 `/skill-doctor`（[changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)）：显示**当前会话**已加载技能及上下文成本——但为**会话内交互式命令**，非可编程跨会话 API；另有 `Skill(name)` deny 规则与 `skillOverrides` 托管设置，均属配置层控制 | ❌（见下注） |
| Codex / Cursor / WorkBuddy / Reasonix / OpenCode / DSH / Hermes Agent / TRAE | 均未发现公开的运行时技能集查询 API | ❌ |

> **注（触发条件语义澄清）**：`/skill-doctor` 只反映**其所在会话启动时**的
> 加载结果，而会话启动加载即读 skills 目录的文件系统真相——与本工具配置层
> 审计同源同构，不产生新增信息；且外部工具无法附着到他人正在运行的会话
> （无 IPC 面），新起会话探测又会引入写副作用与成本，违背只读边界（ADR-19）。
> 故「可查询的运行时技能集 API」的合格标准为：**可编程、可跨会话附着或
> 无副作用探测**的接口——当前仍无客户端满足。

**结论**：三条重开触发条件均未满足（触发 1 部分接近但不合格；触发 2/3 无新
证据），**维持延后定案**。下次复核时点：任一客户端发布可编程运行时技能/
工具集查询接口，或 #36868 类泄漏波及 skills 目录的证据出现。

### D14 skill-mcp-manager 竞品核实（定案：互补不重叠）

**核实方式**（2026-09-04 网络调研，一手材料）：[alone-tree/dsh-skill-mcp-manager](https://github.com/alone-tree/dsh-skill-mcp-manager) README（repo 现已可达，立项评估时不可达）、[npm 包](https://www.npmjs.com/package/dsh-skill-mcp-manager)、[LobeHub 条目](https://lobehub.com/zh-TW/mcp/driftingradiance-skill-mcp-manager-skill)。

**它是什么**：DeepSeek Harness（DSH）的**宿主级插件**「能力库（Capability）」——DSH 设置页内的 SKILL/MCP 可视化管理 + MCP **按需加载**（目录只暴露 name+描述，会话内 `mcp_load` 热加载、按会话独立实例）、SKILL 深扫（任意深度 `SKILL.md`）、隐藏技能（写 `disable-model-invocation`，对模型不可见但 `/` 命令仍可用）、单工具黑名单、原生 MCP 配置接管/卸载归还、仅作用于所装 profile。MIT。

**与 skill-mcp-studio 的关系——不同层、不同域，互补不重叠**：

| 维度 | dsh-skill-mcp-manager | skill-mcp-studio |
|------|----------------------|------------------|
| 作用域 | 单一 DSH 宿主、单 profile（明示「no overreach」） | 8 个异构客户端的跨客户端治理 |
| 层次 | 运行时/会话层（token 经济、热加载、按会话实例） | 配置/文件系统层（安装证据→路径合规→配置正确→端点活体探测→启停一致性五层验证） |
| 启停语义 | DSH 原生标记（`disable-model-invocation`、工具黑名单） | 符号链接存在性 + 漂移审计（ADR-17/21） |
| 端点治理 | 无（管理本地 MCP 注册表） | 统一 Hermes 端点归一 + legacy 通道收口 |

**衔接点**：其 `disable-model-invocation`/黑名单正是第 7 项 `native_disable` 只读挂载点设计的用例——若未来本机安装该插件，可在 DSH 注册表条目声明 `native_disable` spec 直接读入，零代码接入。

**本机影响**：已核实本机**未安装**该插件（无 `~/.dsh/skill-mcp-manager/`，`cordis.patch.yml` 无条目），第 7 项「8 客户端均无原生按技能禁用标记」的调研结论不受影响；DSH 客户端继续由本工具 L2/L5 管理。

### D15 UNMANAGED 小尾巴收口：`.copilot` 注册 + `.cc-switch` 豁免（定案）

**背景**：`--discover` 下 `.copilot`/`.cc-switch` 报 UNMANAGED 且 `result_ok` 判不合规。

**实态核实（本机）**：两者均为指向统一仓库的根符号链接（同步脚本批量建立）。`.copilot` 是 GitHub Copilot 的技能目录（技能消费客户端）；`.cc-switch` 是 Claude Code/Codex 提供方切换器（CC Switch.app，内含 `cc-switch.db`），链接属同步产物。

> **更正（FEAT-6，见 D18）**：本条的「不消费技能」是**错的**。CC Switch 带完整技能管理功能
> （其库中 `skills` 表 186 条、`skill_repos` 远端仓库若干），它是技能的**管理/安装者**，
> 只是不把技能喂给某个 agent 去跑。故它**是**技能挂载点，**不是** IDE/Agent。下文
> 「否决注册」的结论已在 D18 按「非 IDE/Agent 客户端」身份重新定案。

### D18 非 IDE/Agent 的客户端身份 + Codex MCP 丢失根因（定案 + 已执行）

**背景 A（显示身份）**：CC Switch（`com.ccswitch.desktop`，装于 `/Applications/CC Switch.app`）在自动发现下被登记成带点的目录名 `.cc-switch`、类型推断为「AI Agent」、安装状态因发现条目缺 `install` 段而误判 `none`，再被 UI 的 `install_state !== "none"` 过滤掉——**「看不见」是安装判定失败导致的巧合**，一旦修好安装判定它就会冒出来并被算成一个 Agent。

**定案 A**：在 `config.yaml` 的 `tools` 段给它正规身份（`name: CC Switch`、`type: 配置工具`、`install.app_bundles`、`skills_paths: [~/.cc-switch/skills]`、**`non_agent: true`**）。因 `effective_tools` 按**归一化名**去重（`.cc-switch` 与 `CC Switch` 同归一为 `ccswitch`），该声明与发现条目**字段级合并**，幽灵条目随之消失、名字与类型被修正。可见范围明确为：**技能审计可见**（186 技能，`skills_compliant` 转正、审计退出码 0）、**IDE/Agent 表与统计不可见**（快照 `is_agent: false`，前端统一经 `_agentsForPanel()` 取数）、**MCP 面板不出现**（它不消费 MCP，它是把 MCP **注入**别的客户端）。同时把 `cc-switch` 从 `scanner.py` 的「AI Agent」类型关键词移除，消除与「非 AI Agent」注释的自相矛盾。

**背景 B（Codex MCP 每次切换/升级后丢失）**：根因在 CC Switch 侧，其源码注释即自陈：**「重写 live 会整体替换 `config.toml`（有意设计），`[mcp_servers]` 随之丢失，写完必须立刻从 DB 重新投影启用的 MCP」**（`services/provider/mod.rs`），随后 `project_servers_to_app` 按注册表**逐条 reconcile**：`enabled` 的重写回 live、`!enabled` 的从 live 删掉。故 `[mcp_servers]` 是 CC Switch 注册表的**投影产物**，凡不在其 `mcp_servers` 表（`enabled_codex=1`）中的条目每次切换必被丢弃。

**实证对照**：同一次切换中 `hermes-nas`（在注册表、`enabled_codex=1`）**存活**，而 `K8s-uat`/`hermes`（不在注册表）**消失**——唯一变量正是「在不在注册表」。

**定案 B**：**不要**把端点写进 CC Switch 的「通用配置」（`settings.common_config_codex`）——实测被其自身回滚（3132 → 2854 字节），且其源码有 `strip_codex_mcp_servers_from_settings` 从存储的 provider 配置中主动剥离 `mcp_servers`，明确不接受该路径携带 MCP。**正确做法**是把端点注册进它的 `mcp_servers` 表并置 `enabled_codex=1`（形状：`{"type":"http","url":…,"headers":{…}}`，DB 用 `headers`、写 TOML 时转 `http_headers`）。已在停用 CC Switch 的前提下执行并验收通过：真实切换后两端点**存活**，探活 `mcp_initialize_ok`/`mcp_tools_list_ok` 均 true。
**残余兜底**：应用侧 DATA-8 漂移识别（`backup exists + expected missing` = 疑似被外部改写）+ 一键「回流」仍在，覆盖任何未纳入注册表的端点。
