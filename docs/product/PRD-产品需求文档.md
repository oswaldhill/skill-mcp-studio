## 1. 应用范围（跨平台）

### 1.1 目标环境

skill-mcp-studio 是**跨平台**的本地桌面工具，同一份代码在三类环境运行：

| 环境 | 口径 | 路径规范 | 交付形态 |
|------|------|----------|----------|
| **Windows** | 支持 | `%USERPROFILE%`（家目录）、`%APPDATA%`（Roaming）、`%LOCALAPPDATA%`（Local） | **MSI 安装器** |
| **macOS** | 支持（当前已实现） | `~`、`/Applications`、`~/Library`、`~/.config` | `.app` / `.dmg` |
| **Linux** | 支持「主流」口径 = Ubuntu / Debian / Fedora(RPM) + XDG + portable(AppImage) | `~`、`~/.config`（XDG 优先）、`~/.local`、`/usr/share/applications`、`/opt` | `.deb` `.rpm` `.AppImage` |

> 架构结论：必须摒弃「macOS 中心」的路径硬编码，采用**跨平台分派**（决策 A，见 §1.3）。
>
> **实况勘正（v1.5，2026-10-25 实测）**：本节此前写「当前代码仅含 macOS 路径，且全项目无 `sys.platform` 分派逻辑，Windows/Linux 支持为空白」——**该表述已不成立**，属未回写的历史状态：
> - 注册表已按平台分派：`core/mainstream_registry_data.py` 的 `_current_os()` + `by_os` 覆盖，实测含 **20 处 `windows`、21 处 `linux`** 路径覆盖；
> - CI 三平台构建已就位：`.github/workflows/build-macos.yml`（`macos-14`）、`build-windows.yml`（`windows-latest`）、`build-linux.yml`（`ubuntu-22.04`）全绿；
> - 仍**未闭合**的是「运行时冒烟」：本轮开发机为 macOS，Windows/Linux 侧只验到构建与单测通过，未做真机 GUI 冒烟。该项保留在缺口看板（#6）。

### 1.2 三类扫描路径

自动扫描覆盖三类路径，各平台默认值见《跨平台路径矩阵-Windows-Linux.md》：

| 类别 | 对应字段 | 说明 |
|------|----------|------|
| **Skill 路径** | `skills_paths` + `unified_skills_dir` + `auto_discover.scan_paths` | 每个客户端的技能目录位置、共享技能仓库、自动发现的技能扫描根 |
| **IDE 路径** | 客户端 `app_bundles`（GUI 应用）+ 部分 `config_paths` | 桌面 IDE 的安装位置与配置目录 |
| **Agent 路径** | 客户端 `commands`（PATH 可执行）+ `config_paths` + Agent 型条目的 `type` | AI Agent / CLI 助手的可执行命令与配置目录 |

> IDE 与 Agent 在实现上共用同一份客户端注册表（`mcp_tools` + `tools`），用 `type` 字段区分（AI IDE / AI Coding Assistant / AI Agent / AI Coding Plugin / AI Desktop Client）。「IDE 路径」「Agent 路径」落到实现是**同一注册表路径字段的三平台化**。

### 1.3 路径建模（决策 A：已定）

- 每个客户端声明 `paths_by_os: { "darwin": {...}, "windows": {...}, "linux": {...} }`，运行时按 `sys.platform` 取当前平台那份。
  > **实现落地名（v1.5 勘正）**：实际字段叫 **`by_os`**（不是 `paths_by_os`），落在 `core/mainstream_registry_data.py` 的 `_entry(..., by_os=...)`，由 `_current_os()` + `_pick()` 解析；平台键为 `darwin` / `windows` / `linux`，缺省回落 macOS 默认值（`_pick` 的 `default` 参数）。本文此处以**实现字段名为准**，`paths_by_os` 仅作设计期叫法保留。
- 三平台通用字段仍在顶层兜底（`commands` 中跨平台一致的 CLI 名如 `claude` / `codex` 可只写一份）。
- **消费点收口**：新增统一分派层（建议落在 `core/tool_registry.py`），把「当前平台的 `install.app_bundles` / `install.commands` / `install.config_paths` / `skills_paths` / `config_path`」解析成一套平台无关视图，供 `detect_installation`、scanner、combined_checker、mcp_fixer、management_snapshot 等 10+ 处消费点调用，避免各处散写 `sys.platform`。
- **Windows 路径展开**：`expanduser` 需扩展为同时展开 `%USERPROFILE%` / `%APPDATA%` / `%LOCALAPPDATA%`（`os.path.expandvars` + 平台映射）；Linux/macOS 沿用 `~` 展开。

### 1.4 内置客户端清单（以主流注册表为唯一事实源）

内置默认清单分两类（国际 / 通用 + 国产），**实测 38 条**（v1.5 勘正：本文此前写「22 个」，那是 v0.7 时代的设计目标快照，此后新增的 QwenWork、TraeWork、Trae CN、Cherry Studio 等均未回写）。完整路径 + 确定度 + 来源 URL 见 [`跨平台路径矩阵-Windows-Linux.md`](../design/跨平台路径矩阵-Windows-Linux.md)。**条目数量与路径以 `core/mainstream_registry.py`（`register_mainstream_tools()` 返回值）为唯一事实源**，本文的「38」同样是快照，后续新增以注册表为准，不再回写本段落计数。

实测条目类型分布（v0.31.3，`register_mainstream_tools()` 共 38 条）：AI Agent 16 / IDE Plugin 12 / AI IDE 8 / AI Assistant 2。其中本机已发现 23 个、Skills 侧有挂载的 5 个——**「注册表条数」≠「本机受管客户端数」≠「有 Skills 挂载的客户端数」**，三者不得混用（旧文本把三者当成一个数）。

**国际 / 通用（15 个）**：Claude Code、Cursor、VS Code、Windsurf、Codex、Gemini CLI、OpenCode、Aider、Cline、Roo Code、JetBrains(IDEA/PyCharm/WebStorm)、Zed、TRAE、Goose、Cherry Studio。

**国产（7 个）**：CodeBuddy、WorkBuddy（腾讯）；Qoder、QwenWork 千问办公（阿里）；Trae、TraeWork、豆包 Doubao（字节）。

> **为什么下面只列 22 个名字、注册表却有 38 条（v1.5 说明）**：注册表把**同一产品的多个变体拆成独立条目**——JetBrains 族的 IDEA / PyCharm / WebStorm 各算一条、Trae 与 Trae CN 分开、QwenWork 与其办公版分开，加上每条还可能带 `aliases`（别名不新增条目）。因此「产品名 22 个」与「注册表条目 38 条」都是对的，**但它们是两个口径，不能互相印证**。需要精确数字时以 `register_mainstream_tools()` 为准。

> **无 Linux 桌面版，Linux 扫描直接跳过**：QwenWork 千问办公（仅 macOS/Win/HarmonyOS）、TraeWork（桌面版仅 macOS/Win）、豆包（仅网页版）。
> **无本地 skills/MCP 语义，只判安装不参与 skills/MCP 检查**：豆包（通用对话助手，非编程 IDE）。

### 1.5 内置默认路径的确定度口径

内置默认路径按确定度标注，绝不虚构：

- **verified**：官方文档 / 源码核实（如 Claude Code、Codex、Gemini、OpenCode、VS Code、Zed、Goose、CodeBuddy、Qoder、QwenWork、Trae 的配置与技能路径）。
- **best-effort**：仅基于 VS Code fork / Electron 惯例或社区来源推断（如 TRAE、Cherry Studio、豆包、部分 `%APPDATA%` 映射）。
- 查无权威来源的字段**留空**并标注，扫描时不参与安装判定（如 Aider 的 skills、VS Code 的 skills 目录、JetBrains 的 MCP 文件、豆包的 skills/MCP）。

完整矩阵（22 客户端 × Windows/Linux × 5 字段 + 来源 URL）见 [`跨平台路径矩阵-Windows-Linux.md`](../design/跨平台路径矩阵-Windows-Linux.md)。

## 2. 产品概述

**一句话定位：本地多客户端的 Skill / MCP 通用管理台**——竞品负责「安装与同步」，skill-mcp-studio 负责「检查、管理与修复」。

skill-mcp-studio 是一台面向开发者的**管理型桌面应用**（Tauri 2 + 通用 CLI 引擎），用于：

1. **IDE / Agent**：检查本机所有 IDE / Agent 的安装状态与配置正确性（声明 + 自动发现 + 手动三来源）；
2. **Skills**：管理共享 Skills 仓库（统一目录 vs 单独目录判定、一键合并、逐技能启用状态、版本展示与更新检查、市场安装/升级、**升级前自动备份与回滚**、使用统计）；
3. **MCP**：管理多个 MCP endpoint（端点库 + 每客户端多端点挂载 + 逐端点探活与能力验证）；
4. **跨设备**：用用户自己的 WebDAV 空间同步「个人配置」这一小层（不是技能本体，也不是凭据）；
5. **可运维**：启停矩阵与漂移审计、GitHub token 通道提升检查配额、配置导入导出。

核心方法论是「**四层独立验证**」，把「配置对了」和「真的能用」分开，逐项独立报告、不做短路合并。所有写操作复用统一的「备份 → 原子写 → 校验 → 回滚」安全链。

| 属性 | 值 |
|------|-----|
| 产品形态 | 桌面 App（Tauri 2），webview 装载单文件 `gui/dashboard.html` |
| 引擎层 | Python CLI（`scan.py`，≥ 3.11），core/ 审计引擎 |
| 当前版本 | 见 `version.json` / `CHANGELOG.md`（单一真相，不在文档内快照） |
| 交付物 | `.app`（macOS）+ `skill-mcp-studio` 控制台命令 |
| 数据源 | `config.yaml`（客户端注册表 + endpoint 库）+ 仓库外 `profile_sources` 覆盖 |

## 3. 背景与问题

同时使用多个 AI 编码助手（Claude Code、Cursor、Codex、Windsurf、OpenCode、DSH 等）的开发者，面临三类治理痛点：

1. **变更后体检**：升级、换机、改配置后，不知道哪些客户端掉线、哪些能力缺失。
2. **一致性治理**：多客户端接入同一套 Skill / MCP 时，路径是否都指向统一仓库、端点是否都配置正确，缺乏对齐核查手段。
3. **安全修复**：统一端点迁移时，批量改写各客户端配置需要「可回滚」的安全保障，避免越改越坏。

现有同类工具集中在「安装分发 / 一键启停 / 目录治理」，**「审计验证 + 可回滚修复」是空白带**。skill-mcp-studio 填补这一空白，并从「验证器」演进为「管理器」。

## 5. 产品形态

### 5.1 形态模型

```
┌───────────────────────────────────────────────────────────────┐
│  L2  桌面 GUI（Tauri 2 · 七页管理台 · 浅/深双主题）              │
│       webview 装载 gui/dashboard.html，注入 run_audit / run_cli │
├───────────────────────────────────────────────────────────────┤
│  L1  通用 CLI（scan.py）                                        │
│       只读审计 + 显式写操作 + --dry-run + 多格式机读报告          │
├───────────────────────────────────────────────────────────────┤
│  L0  审计/修复引擎（core/）                                      │
│       四层验证 · 多格式配置解析 · 备份-原子写-回滚 · 报告          │
├───────────────────────────────────────────────────────────────┤
│  配置层  config.yaml + profile_sources（源代码事实）              │
│       客户端注册表（mcp_tools/tools/auto_discover）+ endpoint 库 │
└───────────────────────────────────────────────────────────────┘
```

### 5.2 三条贯穿式硬约束

1. **审计与修复分离**：写操作永远需要显式触发（CLI `--fix-*` / GUI 点按钮），只读审计绝不隐含写入。
2. **单一 source of truth**：客户端注册表 + endpoint 库是唯一事实源，CLI 与 GUI 共享同一引擎产出，结论一致（`scripts/verify_gui_consistency.sh` 作为回归 gate）。
3. **形态向上兼容**：每个形态复用下一层引擎与数据契约，不做推翻式二次实现。

### 5.3 页面结构（七页）

| 页面 | 职责 | 性质 |
|------|------|------|
| **概览** | 六项 KPI（受管客户端 / 已安装 / 仅发现配置 / 未安装 / 统一技能 / 主流已纳入）+ 快捷操作 + **独立的端点连通性区** | 只读 + 快捷入口 |
| **IDE / Agent** | 客户端安装状态、Skills 路径合规、挂载端点 | 业务（纳入 / 移出客户端） |
| **Skills** | 技能清单、每客户端启停状态、客户端挂载矩阵 | 业务（一键合并、逐技能启停） |
| **MCP** | 每客户端 MCP 条目分类（已挂载 / 旧通道 / 未纳管）与覆盖矩阵 | 业务（挂载视图） |
| **Hook** | 生命周期 Hook 事件词表（47 事件）、每客户端接入状态、写入 / 移除 | 业务（Hook 写入） |
| **变更详情** | 后台巡检快照 diff、已接受 / 忽略的变更管理 | 业务（变更通知与回溯） |
| **设置** | 通用配置：统一技能目录、MCP 端点库、自动发现、Hook 命令模板、关于 | 通用（集中管理） |

> **页面演进说明**：Hook 页与变更详情页自 v0.25.0 起交付（`data-page="hooks"` / `data-page="changes"`），本文 v1.2 及之前写「五页」系未回写的过期口径，v1.3 勘正。

> **概览页不含「MCP 探活」KPI（v1.6 勘正）**：此前本节写概览含「MCP 探活」，实际该卡片已被**移除**（代码注释明确记录「探活统计已整体移出本函数」）。原因是它会让用户误以为总览的颜色把端口通断也算进了配置合规结论。现在概览只放六项配置侧 KPI，端点连通性在概览页下方**独立的「端点状态」区**呈现（`--endpoint-status`，与后台巡检同源）。职责分离：**配置审计与连通性探测不混在一个数字里**。

> **通用 / 业务分离原则**：通用配置（能跨所有客户端起作用的全局项：统一技能目录、MCP 端点库、自动发现、活动 endpoint）收敛进「设置」页；只涉及具体客户端 / 具体技能 / 具体挂载的业务动作放在对应管理页。

> 安装已失效）/ `repo_outdated`（仓库待同步，走仓库同步）。后两态**必须单独报数**：

> ② `npx` 重装对仓库形态技能无效，只会得到一条假失败。故任何「有多少个可升级」的呈现
> 一律取 `summary.outdated`，`missing` / `repo_outdated` 各自单列。

#### 6.2.1 技能关闭（长期未使用清理）—— **需求，未实现**

**背景（用户提出，2026-10-25）**：已启用的技能会向模型提供说明并占用上下文。
技能装得越多、真正在用的越少，上下文就被越多「从来不触发」的技能占着。用户
在一款同类工具里见到这样的提示并被它说服：「261 项技能、插件或 MCP 已至少
14 天未使用，建议检查后关闭」，附勾选清单、`不再提醒` 与 `一键关闭`。本工具
当前只有**逐技能、逐客户端**的启停开关，没有「按使用情况批量找出来再一键关掉」
这条路——192 个技能一个个点是不现实的。本需求把这条路径补上。

**定位**：这是现有两件事的组合，**不需要新的写路径**——
判定数据来自已有的技能使用统计（FEAT-10，`--skill-insight`，已产出
`summary.never_used` 与每个技能的 `last_used`）；
关闭动作复用已有的启停写入（`--disable-skill`，符号链接移除 + 备份原子回滚）。
本需求要补的是「**筛选 → 勾选 → 批量关闭 → 提醒节流**」这一层编排与界面。

**功能需求**：

| # | 需求 | 类型 | 要点 |
|---|------|------|------|
| R1 | 长期未使用检测 | 读 | 已有 `last_used` / `never_used` 直接复用；「从未使用」与「N 天未使用」分开呈现，不得混为一个数（实测本机：已装 193、用过 22、`never_used` 171——分开报才不会让人误以为 171 个都「14 天没用」） |
| R2 | 阈值可配 | 读 | 默认 14 天；可选 7 / 14 / 30 / 90 天与「仅从未使用」。阈值必须显示在提示文案里，不能只说「很久没用」 |
| R3 | 候选清单 + 勾选 | 读 | 每行显示技能名、最后使用日期（或「从未使用」）、当前启用客户端数与 N/M 徽标；默认**全选**但允许逐项取消 |
| R4 | 批量关闭 | 写（业务） | 一次确认后批量执行 `--disable-skill`；**逐个技能、逐客户端**执行并可部分成功，结果按技能回报成功/失败与原因，不得只报一个总数 |
| R5 | 关闭前预览与代价说明 | 读 | 明确写出：关闭只移除客户端目录里的符号链接，技能本体与共享库内容**不删除**；随时可在技能页重新开启 |
| R6 | 提醒节流（`不再提醒`） | 写（本地） | 用户可对本次提示选择不再提醒；节流状态存本地（`data/local_overrides.yaml` 同层），不写 `config.yaml` |
| R7 | 入口与触发时机 | 读 | 技能页提供「清理未使用」入口；启动时不弹窗打断（与现有「无横幅打扰」纪律一致），仅在该页给出可关闭的提示条 |
| R8 | 与 MCP 的边界 | 边界 | 同级工具把技能、插件、MCP 混在一个清单里。本工具**不混**：MCP 条目的清理走 MCP 页既有分类（旧通道 / 未纳管），技能关闭只处理技能；两者可分别提示，但不得合并成一个数字 |

**判定口径（必须写进实现与文案）**：

- 「关闭」= 该技能在某客户端目录下的那条符号链接被移除，`--list-skill-states` 里
  该客户端显示 `off`；**技能仍在共享库**，其他客户端不受影响。
- 只有 `per_skill` 形态的客户端能被逐技能关闭；`root` 形态（整目录一条符号链接）
  必须**先迁移**（`--migrate-skill-links`），否则批量关闭会失败——UI 要在执行前
  就把这类客户端标出来，而不是让用户点了之后逐条失败。形态判据取快照里每个
  客户端的 `skill_link_form`（`root` / `per_skill` / `mixed` / `n/a`）；本机实测
  `DeepSeek Harness` 就是 `root`，因此这条不是理论边界。
- 「从未使用」与「N 天未使用」都依赖会话日志扫描结果：日志不全（新装、日志被
  清、换了会话目录）时 `last_used` 会偏旧，因此**不得**把它当成「这个技能没用」
  的绝对结论。文案要写「按本机会话日志统计」，并给出「仅从未使用」这个更保守
  的选项。
- 关闭不删除共享库内容，因此不触发「删除型」二次确认；但批量关闭仍要一次确认
  并显示将影响的技能数 × 客户端数。

**验收（DoD）**：

- [ ] 技能页可列出「长期未使用」候选，文案含阈值与本机会话日志口径；
- [ ] 可勾选/取消，默认全选；显示「将关闭 N 个技能，涉及 M 个客户端链接」；
- [ ] 一键关闭逐个执行、部分成功也如实回报每个技能的结果与失败原因；
- [ ] `root` 形态客户端在执行前被识别并给出「先迁移」的明确指引，不产生一串失败；
- [ ] 关闭后 `--list-skill-states` 与技能页 N/M 徽标同步变化，技能本体仍在库中；
- [ ] `不再提醒` 生效且重启后保持，状态落在 overlay 而非 `config.yaml`；
- [ ] 门禁断言覆盖判定口径与「不得与 MCP 混成一个数字」这条边界。

**刻意不做**：按使用频率自动关闭（不替用户做决定）；云端/跨设备使用统计同步
（会话日志属本机事实，跨设备汇总会得出误导结论）；把技能从共享库删除（那是
另一个动作，且现有「删除」语义已由整理/回收站承担）。

## 7. 非功能需求（质量属性）

| 属性 | 要求 |
|------|------|
| **安全修复** | 所有写操作走「备份 → 原子写 → 写后校验 → 失败回滚」；symlink 用 `os.symlink(tmp)+os.replace` 原子替换，无删除窗口 |
| **dry-run** | 有破坏性的写命令一律支持 `--dry-run` 预览 |
| **安全边界** | GUI 的写命令经 Rust `run_cli` 白名单收口，禁止重定向类参数（`--config` / `--profile` / `--active-profile` 等升级面） |
| **GUI / CLI 一致性** | `scripts/verify_gui_consistency.sh` gate 绿，GUI 审计结论 == CLI 审计结论 |
| **只读默认** | 无参数 CLI 运行是只读；`--full` 绝不隐含 git/cleanup/fix |

## 8. 产品边界（刻意不做）

- **不做**技能市场 / 商店**平台**（agentregistry、gh skill 领域：不建索引、不做排行、不托管分发）。
  > **v1.5 勘正（原表述与已交付能力打架）**：本条此前写「不做技能市场 / 商店」，但 v0.30.0 起已交付 `--market search` / `--market-install` / `--market-upgrade`，界面上也有市场页。这不是违例，是**原表述太粗**。精确边界如下：
  > - **做**：作为「客户端」消费上游已有分发体系——按用户给的包名（`owner/repo`）检索 skills.sh、安装到统一库、把已装技能升级到上游最新版，并在升级前自动备份、可回滚。价值在于**把上游的东西装进来后管好**，与审计主线一致。
  > - **不做**：不自建市场/商店（不做全量索引、排行、评分、推荐、付费、托管分发），不替上游做分发决策。市场源本身**用户可增删改**（`--set-market-source`），默认 skills.sh 只是默认值而非产品立场。
  > - 判据：若某需求会让本工具**成为分发方**（托管技能包、对外提供安装源、承诺可用性），属于「不做」；若只是**消费方**（按需拉取、比对、回滚），属于「做」。
- **不做**多用户权限体系与云端托管（企业级平台，部署成本不符）。
  > **v1.5 勘正（原表述与 WebDAV 交付冲突）**：此处原写「不做…云端同步」「不做云端托管与跨设备实时同步」，而 v0.31.1 已交付 WebDAV 跨设备配置同步。二者需要**分开**：本工具是本地工具，不自建云、不做实时协同、不同步技能包与凭据；但它**可以**用用户自己的 WebDAV 空间搬运「个人配置」这一小层（3 个 yaml/json），且冲突不自动合并、只留档覆盖。判据：**搬运的是用户自己的存储、内容是配置而非资产、非实时**——满足则做，否则不做。
- **不内置任何特定工具的 Hook 命令**：Hook 写入命令完全由用户在 `config.yaml` / GUI 自行配置，产品不预设任何第三方工具的命令（v0.29.0 起剥离 ai-memory 后确立）。
- **不内置 MCP server 远程入口**：v0.29.0 不提供 MCP server 远程配置入口（`unified_mcp_server.py` 已删除），远程配置留待 v0.30+ 专项立项。
- **按需加载 / 逐技能启停已落地（v1.5 勘正）**：原写「按需加载（阶段四 L5）作为增值层，立项时独立决策」，实际已交付——逐技能 × 逐客户端启停（`--enable-skill` / `--disable-skill`，符号链接存在即启用）、启停矩阵（`--list-skill-states`）、漂移审计（`--audit-skill-states`）、形态迁移（`--migrate-skill-links`）。仍属「增值层」的是**运行时按会话加载**（会话级注入），那部分仍未做。

1. **一条需求横跨两种形态（§6.2.1）**：技能关闭对 `per_skill` 客户端可用、对

   修复路径在 X」,否则用户会以为按钮坏了。
