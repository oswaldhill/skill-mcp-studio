## 0. 摘要（一页看懂）

- **定位**：本地多客户端的 Skill/MCP 通用管理工具——检查本机所有 IDE/Agent 的安装与配置、管理共享 Skills 仓库（统一/单独目录、一键合并）、管理多个 MCP endpoint（端点库 + 每客户端挂载 + 逐端点探活）。
- **阶段五转向（2026-09-05）**：早期阶段（一~四）交付的是「只读审计看板 + CLI 修复」；阶段五按用户需求把产品重塑为「管理型桌面 App」——**管理台（现七页，见 PRD §5.3）**、GUI 直接写操作（含备份回滚）、多 MCP 端点库与每客户端多挂载。「三栏」仅为其演进中间态表述，最终形态以 PRD §5.3 为准。本文其余章节的历史表述（如"刻意不做写入型 GUI"）以阶段五设计文档为准。
- **差异化**：四层独立验证（安装证据 → 路径合规 → 配置正确 → 端点活体探测），多格式配置解析（已覆盖 7 客户端），备份—原子写入—回滚的安全修复工作流。
- **资产现状**：skills-mcp-unifier 已具备约 5700 行引擎（18 个模块）与约 1900 行测试（10 个文件），主检查链路已是配置驱动；但 profile 专属逻辑（hermes_checker、网关个人常量）仍留在 core/ 与入口脚本中，这是阶段一的主要改造对象。
- **路线**：阶段一 endpoint profile 抽象（1–2 周）→ 阶段二 CLI 通用化（2–4 周）→ 阶段三 Tauri 图形层（1–2 月）→ 阶段四 按需加载与启停（视需求）→ 阶段五 通用管理台重塑（2026-09-05 起）。
- **立即行动**：按第 5 节的 6 步改造顺序启动阶段一，每步独立验收、全程测试护航。

## 1. 产品定位

**一句话定位：本地多客户端的 Skill/MCP 合规审计与修复工具——竞品负责"安装与同步"，skill-mcp-studio 负责"验证与修复"。**

- **目标用户**：同时使用多个 AI 编码助手（Claude Code、Cursor、Codex、OpenCode、DSH 等）的开发者与团队，尤其是将技能与 MCP 服务集中托管、需要保证各客户端一致接入的场景。
- **生态位**：依据对 14 个同类组件的调研，现有工具集中在三件事上——安装分发（skills-hub 的 47+ 适配器同步）、开关切换（skill-mcp-manager 的一键启停）、目录治理（agentregistry 的注册中心）。审计与修复（安装证据核验、路径合规、配置正确性、端点活体探测、安全修复）是无人占据的空白带。
- **核心判断标准**：沿用并推广 skills-mcp-unifier 已验证的四问模型——客户端是否真实安装、Skills 路径是否指向统一仓库、MCP 是否配置正确、端点是否能 initialize + tools/list 并覆盖所需能力组。配置不等于连接，连接不等于能力，逐项分开报告。

### 3.2 耦合点审计结果（2026-09-01 实测）

对个人拓扑标识（域名、NAS 地址、内网网段等）的全量检索显示，耦合分三层，改造成本差异很大：

**第一层：主检查链路——基本解耦（好消息）。** combined_checker、mcp_fixer、mcp_checker 均从配置文件的 `unified_mcp` 段读取端点名称、URL、legacy 名单与能力组要求，没有把个人拓扑写死在逻辑里。主链路的抽象改造量很小。

**第二层：core/ 内部的 profile 专属模块（初稿遗漏，本次核验新发现）。** 这一层的存在意味着"引擎基本解耦"的结论只适用于主检查链路，阶段一必须同时处理：

- `core/hermes_checker.py`：22 处 hermes/NAS 专属识别逻辑硬编码在模块内（`NAS_GATEWAY_URL`/`NAS_API_KEY` 环境变量启发式、`hermes-nas`/`hermes-memory`/`hermes-gateway` 三通道命名校验、`hermes-bridge.py` 命令识别等），且仍被 scan.py 的 `--hermes`/`--full` 接线使用。它本质上是"hermes-home profile 的连通性检查器"，却住在通用引擎目录里；
- `scripts/unified_mcp_server.py`：虽定位"通用网关"，但内置 `OPS_KEYWORDS` 常量（含个人内网网段 192.168.x./10.x.、设备名等）与按 hermes 能力组写死的 `EXPOSED_TOOL_NAMES`，需随 profile 外置或改为配置注入；
- `core/mcp_checker.py`：第 89 行 docstring 示例中含个人端点 URL，属无害残留，随手清理。

**第三层：部署与周边——硬编码集中地。** 具体分布：

- `deploy/` 目录（9 个文件）：Nginx 配置、安装脚本、docker-compose，全部绑定 NAS Nginx-UI / EasyTier SNI / fnOS 个人网络拓扑；
- `scripts/`：fnos_ingress_keeper.py、cherry-hermes-setup.py、easytier_sni_route_keeper.py 三个脚本绑定个人拓扑；
- `tests/`：6 个测试文件含个人拓扑标识，其中 4 个把端点 URL 直接写死在断言里（test_combined_checker、test_mcp_checker、test_mcp_fixer、test_reporter），另 2 个是拓扑脚本自身的测试（test_fnos_ingress_keeper、test_easytier_sni_route_keeper）；
- `scan.py` 第 463 行附近：修复建议的帮助文本中打印了个人网关 URL 与占位密钥示例（初稿遗漏，本次核验新发现）；
- `references/ide-agent-setup.md` 与 SKILL.md 的叙述部分。

**结论（修订版）**：主检查链路已是配置驱动的，但 profile 专属逻辑仍存在于 core/ 模块、通用网关与 CLI 入口中。阶段一要做的是两件事：把"个人拓扑"从代码库主干移到独立的 profile 包，**并让引擎支持多 profile**——后者包含对 hermes_checker 这类专属检查器的泛化或迁移，不只是改配置读取方式。

## 5. 阶段一详细方案：endpoint profile 抽象

把单一写死的统一端点改造为可插拔的 endpoint profile 体系。个人 Hermes 拓扑变成第一个 profile，而非唯一标准。

### 5.1 配置结构改造

**第 1 步：config.yaml 结构迁移。** 现有 `unified_mcp` 段升级为 `profiles` 集合，新增 `active_profile` 指针：

```yaml
active_profile: hermes-home

profiles:
```

`mcp_tools`、`tools`、`auto_discover`、`unified_skills_dir` 四段保持不变（它们本来就是客户端侧配置，与端点无关）。每工具的 `unified_name` 覆盖机制保留，作用域挂在 profile 下。

**第 2 步：引擎传参。** combined_checker 与 mcp_fixer 已经接收 config 字典，只需在入口处按 `--profile <name>`（默认取 `active_profile`）选出 profile 段，替换现在 `config.get("unified_mcp", {})` 的取法。保留向后兼容：若配置文件仍是旧结构（有 `unified_mcp` 无 `profiles`），自动包装成单一 profile 并给出迁移提示。

**第 3 步：测试参数化。** 6 个含个人拓扑标识的测试文件改为测试夹具常量（定义在 tests 的公共 fixtures 中），测试逻辑不变；新增一组"通用 profile"测试：用假端点验证无 required_capabilities 时只检查 initialize + tools/list 的行为。

**第 4 步：部署层剥离与 profile 专属模块改造。** 两个子项：

- （a）纯文件迁移：`deploy/` 全部 9 个文件与 `scripts/` 中绑定个人拓扑的三个脚本（fnos_ingress_keeper、cherry-hermes-setup、easytier_sni_route_keeper）移入 `profiles/hermes-home/` 子包（或独立仓库），主干代码库不再包含任何个人域名与内网地址。同步清理 scan.py 帮助文本中的个人网关示例与 core/mcp_checker.py docstring 中的个人 URL。
- （b）profile 专属检查器处理：`hermes_checker` 的环境变量启发式与三通道命名校验改为由 profile 声明驱动（profile 中新增如 `legacy_detection` 段描述识别规则），模块本体留在主干泛化为"legacy 接入检查器"；若短期泛化成本过高，退路是整体移入 `profiles/hermes-home/` 并由 CLI 按 profile 动态加载。`unified_mcp_server.py` 的 `OPS_KEYWORDS`/`EXPOSED_TOOL_NAMES` 同理外置到 profile 配置。

**第 5 步：文档重写。** SKILL.md 拆为两部分：通用标准（四问模型、状态模型、安全修复流程——这是产品文档）与 hermes-home profile 说明（个人拓扑细节——这是 profile 文档）。references/ide-agent-setup.md 同步拆分。

**第 6 步：全量回归与行为对比。** 跑全部测试；用改造前后的 `scan.py --full` 报告做逐行 diff，确保默认 profile 下行为零变化。

### 5.2 能力组字段的泛化

状态模型中 4 个能力组字段（hermes_memory_available / ai_memory_available / tdai_available / hermes_available）目前是 hermes 专用的。改造为数据驱动：探测结果按 profile 中定义的 `required_capabilities` 键动态生成字段（如 `capability_hermes_memory`），11 字段模型扩展为"7 个固定字段 + N 个能力组字段"。报告与后续的 GUI 矩阵视图都按此动态渲染。

### 5.3 实施顺序与风险控制

按依赖顺序执行，每步可独立验收：

1. 配置结构迁移 + 向后兼容读取（不动任何逻辑）→ 跑全部测试；
2. 引擎传参改造（--profile 标志）→ 跑全部测试 + `scan.py --full` 对比改造前输出；
3. 测试参数化（消除硬编码）→ 跑全部测试；
4. 部署层文件迁移 + profile 专属检查器改造（文件移动部分不改逻辑；检查器泛化单独提交、单独评审）→ 跑全部测试；
5. 文档拆分 → 人工评审；
6. 全量回归 + 报告逐行 diff → 阶段一收尾。

风险控制：每步之前检查 git 状态、保留无关改动（沿用本工具自己定义的安全工作流）；第 2 步与第 6 步均用改造前后的 `scan.py --full` 报告做逐行 diff，确保默认行为零变化；第 4(b) 步若泛化受阻，启用"整体移入 profile 包 + 动态加载"退路，不阻塞主线。

## 6. 非目标与风险

> **修订（2026-10-16）**：原 §6 三条"明确不做"已有两条被推翻：
> - "不做技能市场" → 已做（FEAT-9，`--market` / `--market-install` / `--market-upgrade`）
> - "阶段三之前不做写入 GUI" → 已推翻（阶段五起 GUI 有写入操作，含备份回滚）
> 以下为修订后的非目标。

**明确不做的**（避免定位漂移）：

- 不做 **SaaS 多租户**：不建云服务、不托管用户数据、不做在线账号体系。本产品是**本机桌面应用**，配置同步走 iCloud / WebDAV 等用户自有存储，不经我们的服务器。
- 不做 **技能编辑器 / IDE**：技能的内容编写（prompt、工具定义）是 IDE / Agent 自身的职责；本产品只管理技能的**安装、启停、链接、版本**，不编辑技能内容。
- 不做 **MCP 端点自身的实现**：端点库管理的是"哪些客户端连哪个端点"，端点后端（如 Hermes Gateway）的实现不在本项目范围内。但本产品提供 MCP 工具接口，允许其他 AI Agent 远程读写配置。

**主要风险**：

1. **竞品跟进验证能力**：若 skills-hub 等头部项目补齐活体探测功能，差异化窗口收窄。对策：把"四层验证 + 安全修复工作流"做深（多格式解析、迁移保护策略），这是需要长期工程积累的部分；
2. **生态碎片化**：各客户端配置格式持续演变（已见 cordis_yaml、jsonc 等非标准格式），注册表维护是长期成本。对策：config.yaml 注册表机制已把新增客户端的成本降为"加一段声明"；
3. **个人项目存续风险**：调研显示该领域多数项目活跃度低。对策：从阶段一起就公开仓库、文档与测试，把"维护可信度"本身作为竞争力；
4. **改造回归风险**：阶段一动的是核心检查链路。对策已内置于 5.3：每步独立验收 + `scan.py --full` 前后逐行 diff + 测试全程护航，任何一步回归都可停在原地修复而不影响后续步骤。

## 6b. 产品治理评估（2026-10-16）

### 角色与流程

本项目当前是"用户即 PM"模式：用户直接拍板所有产品决策（功能取舍、UI 形态、优先级），没有独立产品经理角色。这在项目早期（v0.20-v0.28，功能从 0 到 1）是合理的，因为创始人 = 唯一深度用户 = 产品决策者，决策链路最短。

随着功能增长到 20+ 模块、1200 测试、7 个 GUI 页面、95 个测试文件，需要引入**轻量产品治理流程**，避免决策散落、非目标漂移、路线图过期：
