## Q0-1. Rust 工具链用浮动 `stable`，actions 未钉 SHA

**证据**（`.github/workflows/*.yml` 中全部 `uses:`）
```
uses: actions/checkout@v5
uses: actions/setup-node@v5
uses: actions/setup-python@v6
uses: actions/upload-artifact@v6
uses: dtolnay/rust-toolchain@stable      ← 连大版本都没钉，永远取最新 stable
uses: softprops/action-gh-release@v3
uses: swatinem/rust-cache@v2
```
**影响**：`dtolnay/rust-toolchain@stable` 会在上游发布新 stable 时**无声切换编译器**。
本项目 `Cargo.toml` 用的是 `tauri = "2"` 这类宽松约束，配合浮动的 rustc，
构建失败会以「与本次改动无关」的形式出现 —— 正是本仓库最忌讳的**不可归因失败**。
其余 actions 钉到 major tag（`@v5`）仍可被上游在同一 major 内改动。

**建议**：① `dtolnay/rust-toolchain` 钉到具体版本（如 `@1.98.1`）或 commit SHA；
② 其余 actions 钉 commit SHA；③ 引入 dependabot 统一管理升级（见 Q1-6）。

## Q0-2. 构建 workflow 授予 `contents: write` 过宽

**证据**：`.github/workflows/build-macos.yml:16-17`（三个平台一致）
```yaml
permissions:
  contents: write
```
**影响**：`contents: write` 只有「上传 release 资产」时才需要，而该 workflow 同时被
`pull_request` 触发（`:7-8`）。PR 场景下这一步授权超出所需，属最小权限原则的偏离。

**建议**：把「构建」与「发布」拆成两个 job，构建 job 用 `contents: read`，
仅发布 job 提权到 `contents: write`；或按 job 级 `permissions:` 限定。

### Q0-4. `release.sh --push` 推的是 Codeup，而发布流水线在 GitHub —— 最危险的一处「静默不做」

**证据**
```

scripts/release.sh:238  git push origin "$NEW_TAG"     || die ...
scripts/release.sh:241  打印「release workflow 会被 tag 触发，自动补 Release 正文（release-notes.yml）」

git remote -v
  origin   git@codeup-oswaldhill:oswaldhill/skill-mcp-studio.git   ← 脚本推这里
```

### S1. `--progress-file` 未被拒绝 → 从 webview 取得「写任意路径」的原语

**复核证据**（`src-tauri/src/lib.rs`）

```

355  let first_flag = args.iter().find(|a| a.starts_with("--")).cloned();            ← 只取「第一个」标志
356  if let Some(flag) = first_flag {
```

而同文件 `:136-144` 的注释明确宣称：
> **路径由 shell 独占决定，webview 不能指定** —— 否则 `--progress-file` 就变成
> 一个「往任意路径写 JSON」的写原语，越过了 ARCH-2 的写边界。


即**「分开写成两个参数」才中招**，这也解释了它为何一直没被测试发现。

**建议**（任一即可，建议第一条）：
1. 把 `--progress-file`（以及所有「值型路径参数」）加入 `DENIED_FLAGS`；
2. 不再依赖 token 检测，改为**先剥掉调用方所有 `--progress-file*`**，再由 shell 追加；

   |---|---|---|
   | 「单文件 6316 行」 | **6386** 行 | 后续多轮修复往页面加了代码 |

   | `gui/dashboard.html:8-1448,1643-6314` | `<style>` 在头部；脚本 1646–6383 | 行号同样已漂移 |

   #### 更有用的那个发现：77 = 2 + 75，「内联样式」几乎全在 JS 里

   上面这轮实测顺带把 R2/S2 里「要消掉 77 处内联样式才能去掉 `style-src 'unsafe-inline'`」
   这句话**说准了**：

   · 静态 HTML 里只有 **2** 处 `style="…"`；
   · 另外 **75** 处全部出现在**内联 JS 的字符串模板**中 —— 即这些内联样式是
     运行时由脚本拼进 DOM 的，不是写在标签上的；
   · 挪走脚本后（`gui/dist/app.js`）产物 HTML 里只剩那 2 处，75 处随之进了 `app.js`。

   这意味着那条建议的真实工作量是「**改 JS 里拼 HTML 的 75 处内联样式**」
   （换成 class 或 CSS 自定义属性），而**不是**「清理标签属性」。
   原先的表述会让执行者低估难度、也会找错地方。**这是本轮把话说明白的地方，不是新增工作项** —— S2 的结论（暂不做）不变。

   #### 更正说明（Round 29）：可行，但权衡后不做

   **原理由错在**：它断言「关掉 `withGlobalTauri` 必须引入打包器」，这是**未经验证的前提**。
   读 `tauri-2.11.5` 源码可证其不成立：

   · `src/manager/webview.rs` 的 `initialization_script()` 把 `pattern.js` / `ipc.js` /
     **`core.js`** / 事件初始化脚本**无条件**嵌进 `scripts/init.js` 的 `__RAW_*__` 占位符。
     该函数里**没有任何 `with_global_tauri` 判定** —— 全 crate 里该字段只出现在
     `src/test/mod.rs` 一次。
   · `scripts/core.js:81` 正是：
     `Object.defineProperty(window.__TAURI_INTERNALS__, 'invoke', { … })`。

   即 **`window.__TAURI_INTERNALS__.invoke` 与 `withGlobalTauri` 无关、始终存在**。
   把页面里的 `window.__TAURI__.core.invoke` 换成 `window.__TAURI_INTERNALS__.invoke`
   就能关掉全局命名空间，**不需要任何打包器**。

   **结论仍是不做，但理由换成真实的那条**：`__TAURI_INTERNALS__` 是**下划线前缀的内部
   API，Tauri 不承诺跨版本稳定**；而 `withGlobalTauri: true` 暴露的 `__TAURI__` 才是
   官方公开面。用它换掉公开 API，是「拿稳定性换一点攻击面收敛」。而这点攻击面本来就小：
   页面是自有的本地文件、CSP 已很紧（`connect-src 'none'` / `object-src 'none'` /
   `frame-src 'none'`）、无远程内容。**收益小、失败模式却重** —— 换错等于应用一条原生命令
   都调不通，而这条路径无法在本环境完整冒烟。

   把记录从「不可行」（**事实错误**）更正为「**可行但权衡后不做**」（可复核的工程判断）。

   顺带更正同段一处过时表述：原文写「`frontendDist` 是静态目录 `../gui`」，现已改为
   `../gui/dist` 且新增了构建步骤 `scripts/build_gui.py`。仅措辞过时、**不影响结论** ——
   构建期拆分不等于前端打包器，`@tauri-apps/api` 那条路仍需要后者。

### 若要推进，建议的顺序（都需实机验证）

1. 先让开发态也走 Tauri 自定义协议（而非 `file://`），使 `'self'` 语义与生产一致；
2. 再把内联 `<script>` 外置为 `gui/dashboard.js`（顺带完成 S10 的脚本部分）；
3. 然后去掉 `script-src` 的 `'unsafe-inline'`（**保留** `style-src` 的，页面有 77 处内联 `style=`）；
4. 最后才考虑引入打包器以关闭 `withGlobalTauri`。

## S10 专节：实测证据、暴露的代价、以及为什么回退

### 一、已用真实引擎证明「外置脚本可行」

S2/S10 此前的阻塞点是猜测：「开发态以 `file://` 加载页面时，CSP 的 `'self'`
是否匹配同目录 `.js`」。本轮写了 `WKWebView` 探针（Swift，**Tauri 在 macOS 上用的正是
这个引擎**，不是 Chrome）实测，得到确定结论：

```
[现状 script-src 'self' 'unsafe-inline']
  外部脚本 ext.js : yes          ← 加载并执行成功
```

关键推理：**`'unsafe-inline'` 根本不覆盖外部脚本**（它只覆盖内联块），
所以外部脚本 `ext.js` 能执行，只能是因为走了 `'self'` ——
即 **`file://` 下 `'self'` 确实匹配同目录资源**。

结论：**外置 `<script>` 本身是安全的，不需要改动 CSP。**

**探针自身的两次修正（值得记下）**：

1. v1 两档都「未回报」—— 命令行 Swift 程序没有 `NSApplication` 事件循环，
   WKWebView 根本不会开始加载。**那不是结论，是探针没跑起来。**
2. v2 收紧档报「被拦」—— 但报告是**内联脚本**发的，去掉 `'unsafe-inline'` 后内联被拦，
   于是收不到回报，我却解读成「外部脚本被拦」。**两者无法区分，判定逻辑有 bug。**
   v3 改用 Swift 侧 `evaluateJavaScript` 取值（不受页面 CSP 约束）才排除歧义 ——
   但 v3 因工具落盘问题没跑成，**故收紧档的结论本轮未取得**，不做任何声称。

### 二、代价：15 个测试文件的 114 条断言

实做外置后门禁立刻变红，`unittest` 报 **114 个失败/错误，横跨约 15 个测试文件**：

```
AssertionError: 未找到函数 runSkillInsight
ERROR: test_... (test_advice_layout / test_usage_auto_refresh / test_merge_ui /
       test_design_spec / test_dashboard_*_ui / test_gui_inline_style_csp /
       test_probe_verdict_ui / test_rerun_progress / test_modal_top_layer / ...)
```

根因统一：这些用例都靠 `Path("gui/dashboard.html").read_text()` + 正则抽取
**JS 函数体**来做断言（例如 `_fn("runSkillInsight")`）。脚本外置后函数不在 HTML 里了。

`tests/gui_helpers.test.mjs` 我已改成「优先读 `dashboard.js`、回退 HTML 内联块」并通过（5/5），
但剩余 15 个文件的改造量远大于 S10 本身的价值。

### 三、判断：回退

S10 的收益是**纯组织性**的（单文件拆成 HTML + JS），不改变任何用户可见行为或安全性；
而代价是重写 15 个测试文件、且**极可能在改造过程中削弱断言**（例如把精确断言退化为存在性检查）。
收益/风险不成比例，故**回退**：

```
git checkout -- gui/dashboard.html tests/gui_helpers.test.mjs
rm -f gui/dashboard.js
→ 门禁恢复：961 用例 OK(skipped=2)，工作区干净
```

### 四、若将来要做，正确顺序

1. **先**在 `tests/` 加一个共享取源辅助（如 `tests/_gui_source.py`：
   「优先 `dashboard.js`，回退 HTML 内联块」），把 15 个文件的取源方式统一改过去；
2. **确认门禁全绿**（此时脚本仍在 HTML 里，取源辅助走回退分支）；
3. **再**外置脚本 —— 此时测试已与「脚本放在哪个文件」解耦，外置不会引起任何红；
4. 顺带完成 S2 的前置（外置脚本后，`script-src` 才有可能去 `'unsafe-inline'`，
   但仍受 `withGlobalTauri` 与 77 处内联 `style=` 属性双重约束，见 S2 专节）。

### 五、后续轮次的进展（截至 Round 21）

按第四节的顺序推进，已完成**第 1 步的关键部分**，且发现了一个使代价大幅下降的做法：

**① 取源统一（`96d2c90`）**：新增 `tests/_gui_source.py`，把 20 余处取源收敛到一处。
零行为变更，门禁 961 用例 OK(skipped=2)。

**② 「形态还原」是关键（`0e7b462`）**：`page_source()` 不再做「HTML + JS 拼接」，
而是**把外置的 `<script src="dashboard.js">` 换回 `<script> …脚本全文… </script>`**，
重建 S10 之前的单文件形态。

理由（实测教训）：测试有**两类**取源写法 ——
  · 直接抽 `function xxx` 的函数体；
  · 用 `<script>` 标记**切片/正则匹配脚本块**（`re.search(r"<script>(.*?)</script>")`、
    `s.index("<script>")`、`re.findall(...)`）。
只做拼接时第二类会抓到空串，表现为「未找到 `<script>` 区块」/「substring not found」/
「`'str' object has no attribute 'group'`」——**一次性打掉约 30 个用例**（前三轮的红多半源于此）。
形态还原后，两类写法都无需感知脚本放在哪个文件。

**③ 用外置形态实测的收敛曲线**：114 → 63 → 39 → 58 → **21** 条失败。

**④ 剩余 21 条已定位到行**（5 个文件，共 4 类根因）：

| 文件 | 根因 |
| --- | --- |
| `test_advice_layout.py:17` | 用 `HTML.index("function memberRow")` —— 替身需支持**字符串方法** |
| `test_rerun_progress.py:20` | 同类（`re.search(pattern, HTML)`） |
| `test_modal_top_layer.py` | 同类 |
| `test_cli_contract.py:77` | 内联写法 `(ROOT / "gui" / "dashboard.html").read_text(...)` |
| `test_dashboard_scope.py:150` | 把页面交给 `tools/dash_crash_harness.js`，**需要真实路径** |

对应结论：替身应设计为**两个入口** ——
`source_path()`（继承 `str`，内容 = `page_source()`，另给 `read_text()`/`exists()`）
供「当字符串用」与「当 Path 用」两类写法；`page_path()` 供需要真实路径的外部工具。

**⑤ 两个已踩过的坑（务必避免重犯）**：
  · 替身若继承 `str`，`str(替身)` 返回的是**整页内容**而非路径 ——
    于是 node harness 把 HTML 当 JS 跑，报 `Unexpected identifier 'html'`。
    凡「需要路径」处必须走 `page_path()`。
  · 曾试过把形态还原后的源码写成临时文件再传路径，但 harness 会看文件名/邻居文件，
    对临时文件不成立 —— 故仍用真实路径。

因此：**第四节「15 个文件、114 条断言」的代价评估已被推翻** ——
有了形态还原 + 替身，改造量降到「每个文件一行」级别。S10 从「不值做」变为**值得收尾**。

### 六、S10 落地方式与验证梯度（截至 Round 27）

**最终选择的是「构建期拆分」而非「仓库内拆分」。**

理由：仓库内外置脚本会让 20 余个测试文件失去断言依据（实测 114 条断言失败，见第四、五节）。
改为**源文件保持单文件原样**（既有测试零改动），由构建期生成发布产物：

| 产物 | 内容 |
|---|---|
| `gui/dist/dashboard.html` | 不含内联 `<script>`，改为 `<script src="app.js" defer></script>` |
| `gui/dist/app.js` | 原内联脚本全文（逐字节切片，无损） |
| `gui/dist/assets/fonts/*.woff2` | 页面 `@font-face` 引用的字体（**必须随产物走**） |

产物里的 HTML 特意仍叫 `dashboard.html` —— 因为 `tauri.conf.json` 的
`windows[0].url` 就是它，同名可少改一处、少一个出错点。

**接线**：`src-tauri/tauri.conf.json` 的 `frontendDist` 指向 `../gui/dist`，
并由 `build.beforeBuildCommand` 调用 `scripts/build_gui.py` 生成产物。

#### 验证梯度（每一层都有对应断言或实测）

| 层次 | 覆盖内容 | 载体 |
|---|---|---|
| 产物正确性 | 无内联 script、外链引用、脚本本体完整 | `test_dist_*` |
| 拆分无损 | 拼回源文件**逐字节一致** | `test_split_is_lossless` |
| **产物自包含** | 页面引用的每个相对资源都在 dist 里 | `test_dist_contains_every_referenced_asset` + `--check` |
| 配置一致性 | `frontendDist` 解析、窗口 url 真实存在 | `test_tauri_*` |
| 构建接线 | 命令在**两种 cwd** 下都能跑通 | `test_before_build_command_works_from_either_cwd` |
| **运行期** | 产物在桩 DOM 下完整执行 + 按钮链路通 | `test_split_page_actually_runs_like_the_source_page` |
| 端到端打包 | 真实 `tauri build` 产出可运行包 | 待补，见下 |

#### 两个「切目录」自己引入的坑（都已修，值得记下）

**① `beforeBuildCommand` 的 cwd 是未知量。** `tauri-cli` 是 npm 包、不在 cargo
registry 里，无法从源码确认 hook 的工作目录是仓库根还是 `src-tauri/`；而三个
workflow 是用 `working-directory: src-tauri` 跑 `tauri build` 的。猜错 = 三平台
构建全挂且只能在 CI 发现。于是命令写成四段候选 `||` 链，并在测试里**原样在两个
cwd 各跑一遍** —— 这条测试当场抓到第一版（两段式）在 `cwd=src-tauri` 下退出码 127。

**② 字体没跟着进产物。** 页面在 `@font-face` 里用 `url('assets/fonts/*.woff2')`
引用 3 个字体，它们原本只躺在 `gui/assets/`。原先 `frontendDist=../gui` 时字体恰好
落在嵌入范围内，所以一直没暴露；切到 `../gui/dist` 后 **Tauri 只嵌入这一个目录**，
字体不进产物 → 打出来的包会缺字体（界面回退系统等宽字体 + 控制台 404）。
修法是构建时把 `gui/assets/` 复制进 `gui/dist/assets/`，并让 `--check`
扫描页面所有相对引用、缺任何一个就报错。

**教训**：改「产物目录」这类配置时，必须逐项追问「新目录是否自包含」，
不能只看原来的断言是否还绿。

#### 关于「真实打包」这一环的路径更正

早先以为必须推送到 GitHub 让 CI 跑 `build-*.yml` 才能验证打包，且本仓库
`pre-push` hook 规定「除非显式设置 `GITHUB_PUSH_ALLOW=1`，否则拒绝推送到
github」——于是把它当成需要用户授权的外部阻塞。

**Round 27 更正**：实测 `index.crates.io` 可达（HTTP 200），`cargo search tauri-cli`
可用，因此**本地就能装 `tauri-cli` 并真跑 `tauri build`**，无需推送、无需授权：

```bash
CARGO_TARGET_DIR=~/.cache/sms-cargo-target cargo install tauri-cli --version "^2"
cd src-tauri && cargo tauri build --bundles app
```

#### Round 28：真实打包已跑通，验证梯度最后一层闭合

`cargo install tauri-cli` 装到 **v2.11.5**（与项目用的 tauri 版本一致），
`cargo tauri build --bundles app` 退出码 0，产出 `.app`：

```
Finished `release` profile [optimized] target(s) in 54.52s
Built application at: …/release/skill-mcp-studio
Bundling skill-mcp-studio.app
Finished 1 bundle at: …/release/bundle/macos/skill-mcp-studio.app
```

**做法**：构建前先 `rm -rf gui/dist`，所以产物的出现只可能来自
`beforeBuildCommand` —— 这证明了 hook 在真实 tauri 环境下确实被调用并生效。

**一个必须记住的断言陷阱**：`.app/Contents/Resources` 里**只有 `icon.icns`**，
找不到任何 `dashboard.html` / `app.js` / `*.woff2`。一开始以为打包漏了资源，
其实 **Tauri v2 是把 `frontendDist` 整个编译进可执行文件**，不落成松散文件。
正确的验证方式是查二进制里的字符串与字节魔数：

| 探针 | 命中次数 | 含义 |
|---|---|---|
| `dashboard.html` | 3 | 入口 HTML 被嵌入 |
| `app.js` | 1 | 外置脚本被嵌入 |
| `ibmplexmono` | 3 | 字体文件名被嵌入 |
| `assets/fonts` | 3 | 字体路径被嵌入 |
| `wOF2` | 2 | **woff2 二进制魔数 —— 字体字节真的在 exe 里** |

`wOF2` 魔数是最硬的证据：它只可能来自字体文件本体，不可能由文件名巧合产生。
**至此「产物自包含」这条不只是构建目录里成立，在真实打包产物里也成立。**

七层验证梯度**全部闭合**，不再有待补项。
