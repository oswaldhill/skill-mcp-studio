## P0 — 需要整改

### P0-1. Release 正文被三个平台重复追加三次 —— ✅ 已完成（方案 B，`a349c59`）

**现象**：`v0.23.0` 与 `v0.22.0` 的 GitHub Release 正文都是三条完全相同的内容。

**证据**
- `v0.23.0` Release 正文实测为三行重复的
  `**Full Changelog**: .../compare/v0.22.0...v0.23.0`（`v0.22.0` 同样三行）。
- `build-macos.yml:152-158`、`build-linux.yml:94-101`、`build-windows.yml:120-126`
  **各自**调用 `softprops/action-gh-release@v3`，且都带 `generate_release_notes: true`。
- workflow 注释自述「action-gh-release 对已存在 release 做增量追加」——
  行为符合注释，但结果是无信息量的重复正文。

**已选定方案：B（独立 job 统管 Release 创建与正文）**

实施要点：
1. 三个平台 workflow 的 `generate_release_notes` 一律改为 `false`，
   它们只负责**上传资产**（`action-gh-release` 会在 release 不存在时自动创建空壳）。
2. 新增 `.github/workflows/release-notes.yml`，触发 `push: tags: ['v*']`，
   在三个 build 完成后（用 `workflow_run` 触发、或轮询等待资产就绪）执行：
   - 从 `CHANGELOG.md` 抽取当前 tag 对应段落（`## [vX.Y.Z]` 到下一个 `## [` 之间）；
   - `gh release edit "$TAG" --notes-file <抽出内容>`；若 release 尚不存在则 `gh release create`。
3. **竞态处理**：`gh release edit` 要求 release 已存在。
   首选 `workflow_run`（在三个 build workflow 全部 completed 后触发）避免轮询；
   若坚持同 tag 并发，则需重试若干次。

**验收标准**：新打一个 tag，Release 正文**只出现一份** changelog（内容来自 CHANGELOG），
且三平台共 8 个资产齐全。

### P0-2. 没有 tag 与 `version.json` 的一致性校验 —— ✅ 已完成（`a349c59`）

**现象**：打 tag 时若忘记先 bump 版本，CI 不会拦住，
会产出「tag 名与包内版本号不一致」的发布。

**证据**
- `grep -rn "version.json" .github/workflows/*.yml scripts/*.sh scripts/*.py`
  除 `bump_version.py` 自身外**无命中** → CI 从未读取过 `version.json`。
- 对照：`pyproject.toml:10` 有 `requires-python`，
  说明项目有「声明 + 校验」意识，但发布链路上缺了这一环。

**影响**：错误产物会被签名、上传、分发；tag 一旦推送很难干净撤回。

**建议动作**：在 `test.yml` 增加一步（tag 触发时生效）：

```
- name: tag 与 version.json 一致性
  if: startsWith(github.ref, 'refs/tags/v')
  run: |
    v=$(python -c "import json;print(json.load(open('version.json'))['version'])")
    [ "v$v" = "${GITHUB_REF_NAME}" ] || { echo "tag ${GITHUB_REF_NAME} != v$v"; exit 1; }
```

**验收标准**：故意打一个 `v9.9.9` tag，Test workflow 失败并指出不一致。

### P0-5. `test_stdio_probe` 有一次未定位的偶发失败 —— ✅ 已定位并修复（stderr 管道从未排空）

**现象**：全量跑时该用例偶发报 `stdio handshake timed out`，无法复现。

**证据**
- 一次全量跑中出现：
  `FAIL: test_handshake_and_tool_names ... AssertionError: False is not true : stdio handshake timed out`
  （当时 4 次全量跑中 1 次）。
- 此后复跑 **18 轮**（3 轮全量 + 15 轮专项）**再未复现**。
- 正常握手耗时 0.034–0.057s，预算 5.0s（约 100× 余量）；
  10 路 CPU 满载下该文件仍 0.102s 通过 → 不是纯负载问题。
- **注意**：它不是 CI 失败的原因（真实 CI 日志显示失败在 `test_skill_market_cli`）。

**建议动作**：不急着调超时，先让它**可诊断**：
- 失败时输出子进程实际耗时、stderr 内容、握手在哪一步超时；
- 给 `probe_stdio` 的 stderr 增加「超时时回读已缓冲内容」以便取证。

**验收标准**：下次偶发时，日志足以判定是调度停摆、管道阻塞还是子进程未启动。

**根因（已定位并修复）**：`probe_stdio` 用 `stderr=subprocess.PIPE` 启动子进程，**但整个握手期间没有任何代码读 stderr**（只在 `finally` 里 close）。子进程一旦向 stderr 写入超过管道缓冲（POSIX 通常 64 KiB）就阻塞在 `write` 上，从此不再读 stdin、不回握手 —— 外部只能看到一句 `stdio handshake timed out`。触发与否取决于子进程在握手期间往 stderr 写了多少，这正是它「偶发、复跑不复现」的原因。

- **复现**：子进程先写 200 KiB 无换行 stderr、再正常握手 → 修复前 `elapsed=8.01s`（超时、`initialize_ok=False`）；修复后 `elapsed=0.07s`，握手与 `tools/list` 全部成功。
- **修复**：新增 `_StderrDrain` 守护线程，启动即按块（`read(4096)`）排空 stderr，只保留末尾 2000 字符；`Popen` 增加 `errors="replace"`，避免解码失败把排空线程打退（那会让管道重新被填满）；失败时把 stderr 尾部附到 `result["error"]`，超时不再是一句裸信息。
- **回归用例**（`tests/test_stdio_probe.py`）：`test_noisy_stderr_does_not_block_handshake`（管道阻塞不再发生）+ `test_stderr_tail_reported_when_handshake_fails`（失败可归因）。
- **判据有效性已反向验证**：把排空整个去掉，第一个用例稳定失败（5.0s 超时）；恢复后通过。即该用例确实守住了本缺陷，不是摆设。
- **一处被实测证伪的说法**：先前记录认为「`readline()` 排空会死锁、必须按块读」—— 实测 `TextIOWrapper.readline()` 会持续把数据读进自己的内部缓冲，**同样能排空管道、并不死锁**。选按块读的真实理由是有界内存（`readline()` 对不含换行的 stderr 会无界增长），且 `tail()` 在它返回前一直取不到内容 —— 而这恰恰是最需要取证的输入形态。代码注释已按实测改写。
- **验收**：`scripts/ci_parity.sh` → `Ran 935 tests ... OK (skipped=2)`（原 933 + 新增 2）。

### P0-6. 「禁止未经允许推 GitHub」的门禁 hook **不随仓库生效** —— ✅ 已完成（`a349c59`）

**现象**：门禁只存在于本机 `.git/hooks/pre-push`，**不在版本控制里**，换机器或重新 clone 后自动消失。

**证据**
- `git config --get core.hooksPath` → **未设置**（输出为空）。
- `.git/hooks/pre-push` 与 `scripts/git-hooks/pre-push` 内容一致，说明是**手工拷贝**进 `.git/hooks/` 的。
- hook 自身注释即承认：「本 hook 安装在 `.git/hooks/pre-push`，**不随仓库提交**」。
- 全仓 grep 未见任何安装脚本或 `core.hooksPath` 说明（`CONTRIBUTING.md`、`README.md`、`scripts/*.sh` 均无）。
- 该 hook 是**唯一**拦截 GitHub 推送的机制（拦截文案即「按当前约定，只有在你明确要求时才允许提交 GitHub」）。

**影响**：这是一条**安全/流程约定的单点失效**。
任何一次新克隆、换机、或 `.git` 目录重建，门禁都会静默消失，
而使用者不会收到任何提示——直到某次误推发生。

**建议动作**（二选一，前者更好）：
- **A**：把 hook 目录纳入仓库并由 git 自身加载：
  `git config core.hooksPath scripts/git-hooks`
  （该配置可写入一个 `scripts/install-hooks.sh`，并在 `CONTRIBUTING.md` 说明；
  注意 `core.hooksPath` 本身在 `.git/config` 里，仍需一次安装——但只需一条命令，且可脚本化。）
- **B**：在 CI 侧补一道防线：`test.yml` 中检查「非显式放行时不得出现推送到 github remote 的 workflow 步骤」
  （治本程度弱，因为 CI 拦不住本地误推，但可作为兜底）。

**验收标准**：新克隆仓库后，按文档执行一条命令即可让门禁生效；
或存在 CI 兜底检查且有对应测试。

  即破坏源不止 F401，**`I001` 重排 import 也在其中**。根因与本项目架构强相关：
  大量模块依赖「先注入 `sys.path` 再扁平导入」，并存在跨模块**再导出**
  （A `from X import n`，B 再从 A 取 `n`）。自动重排/删除会静默断掉这两条链路，

- 两轮改动均已 `git checkout` 回退，回退后 `Ran 943 tests, OK (skipped=2)`。

**结论**：本项不能走「先全量 `--fix`、再设为门禁」的常规路径，应作为独立批次按下列顺序做：

1. 给真正的再导出加显式别名（`from X import n as n`）或 `__all__`，让 `F401` 不再误判；
2. 把 `E402` 的 `per-file-ignores` 从 `tests/*` 扩到 `core/`、`scripts/` 里同样做引导的模块；
3. 关闭 `I001` 的自动重排（或对引导点所在文件豁免），**逐文件**确认 import 顺序无害后再启用；
4. 剩余的 `F841`(13)、`E741`(1) 人工过一遍，再用 `--unsafe-fixes` 会改变语义，需逐个看；
5. 最后才加 CI job，并确保首次即绿。

### P2-12 现状侦察（本轮实测）—— 待决策，不宜先行编码

**痛点成因已定位**：

| 事实 | 含义 |
|---|---|

这三条共同导致「改一行 HTML → 必须 `cargo build` + 重装」——即本项要消除的痛点。

**Tauri v2 下的两个候选方案**：

- **方案 A：`build.devUrl` + 静态服务器**
  `tauri dev` 时指向 `http://localhost:PORT`，由一个小静态服务器（如 `python -m http.server`）
  提供 `gui/`。改动集中在配置，不必改 Rust 逻辑；但需要**额外起一个进程**，
  且 dev 与 prod 加载路径不同（前者 HTTP、后者嵌入）。
- **方案 B：运行时分支直读磁盘**
  在 `run()` 中读环境变量（如 `SMS_GUI_DEV=1`），用
  `WebviewUrl::External(Url::from_file_path("gui/dashboard.html"))` 替代嵌入资源。
  更贴合清单原文「WebView 直读磁盘 dashboard.html」，且**不需要额外服务器**；
  代价是要改 Rust 代码并处理 CSP（现配置含 `connect-src 'none'`，
  `file://` 加载下的资源解析需实测）。

### P2-18. 脚本卫生自检（新增，超出原清单范围） —— ✅ 已完成

**来源**：P2-16 第四刀（`mcp_fixer` 拆分）时暴露的真实缺陷，不在原清单 9 项之内。

**问题**：用 `qclaw-text-file` 的 `write_text.py` 重写 `scripts/*.sh` 时，该工具
**新建文件、不继承原权限**，导致可执行位丢失并被提交为 git mode `100644`。后果具有分裂性：

| 调用方式 | 行为 |
|---|---|
| `scripts/xxx.sh`（bash 直接执行） | 正常 —— shell 把脚本交给解释器，**不需要可执行位** |
| Python `subprocess.call([...])` | `PermissionError` —— 需要 `execve` |

于是调用方看到 **`exit != 0` 且日志里没有任何 `Ran N tests` 行**，极易被误判为「测试失败」。
本项目为此**误回滚过一次本来正确的重构**。

**同源问题**：脚本中 `$var` 紧跟全角标点（如 `$cand，`）时，bash 在部分 locale 下会把
标点首字节并入变量名，配合 `set -u` 直接 `unbound variable` 中止脚本 —— 同样伪装成测试失败。

**落地内容**

1. **本地门禁**（`scripts/ci_parity.sh` 新增 1c 段，置于测试之前）：
   - `scripts/*.sh` 的 git mode 必须为 `100755`；
   - `scripts/*.sh` 不得出现「`$var` 紧跟全角标点」，须写 `${var}`。
2. **CI**（`.github/workflows/test.yml` 的 `text-hygiene` job 新增 step
   `Shell script hygiene (P2-18)`）：同样两条，失败以 `::error::` 标注。
   与文本卫生同 job —— 两者都属「会伪装成测试失败」的缺陷。
3. **修正自检抓出的 4 处真实缺陷**：
   `scripts/release.sh:140/210`、`scripts/verify_gui_consistency.sh:37` 的变量写法，
   以及 `scripts/verify_gui_consistency.sh` 的 git mode `100644 → 100755`。

**验证（含反向验证，确认自检不是摆设）**

- 人为写入 `$foo，` → 自检报「全角标点」并中止，**未进入测试**；
- 人为 `chmod 644` → 自检报「可执行位」并中止，**未进入测试**；
- 干净态：两项均 ✓ 且 `Ran 943 tests, OK (skipped=2)`；
- 从 workflow 中抽出该 step 的 `run` 脚本**在本地实跑 exit=0**（不是只看 YAML 表面）。

**给后续的操作规范（两条，务必遵守）**
