## P0 — 需要整改

### P0-1. Release 正文被三个平台重复追加三次 —— **定案：方案 B**

**现象**：`v0.23.0` 与 `v0.22.0` 的 GitHub Release 正文都是三条完全相同的内容。

**证据**
- `v0.23.0` Release 正文实测为三行重复的
  `**Full Changelog**: .../compare/v0.22.0...v0.23.0`（`v0.22.0` 同样三行）。
- `build-macos.yml:152-158`、`build-linux.yml:94-101`、`build-windows.yml:120-126`
  **各自**调用 `softprops/action-gh-release@v3`，且都带 `generate_release_notes: true`。
- workflow 注释自述「action-gh-release 对已存在 release 做增量追加」——
  行为符合注释，但结果是无信息量的重复正文。

**已选定方案：B（独立 job 统管 Release 创建与正文）**

实施要点：
1. 三个平台 workflow 的 `generate_release_notes` 一律改为 `false`，
   它们只负责**上传资产**（`action-gh-release` 会在 release 不存在时自动创建空壳）。
2. 新增 `.github/workflows/release-notes.yml`，触发 `push: tags: ['v*']`，
   在三个 build 完成后（用 `workflow_run` 触发、或轮询等待资产就绪）执行：
   - 从 `CHANGELOG.md` 抽取当前 tag 对应段落（`## [vX.Y.Z]` 到下一个 `## [` 之间）；
   - `gh release edit "$TAG" --notes-file <抽出内容>`；若 release 尚不存在则 `gh release create`。
3. **竞态处理**：`gh release edit` 要求 release 已存在。
   首选 `workflow_run`（在三个 build workflow 全部 completed 后触发）避免轮询；
   若坚持同 tag 并发，则需重试若干次。

**验收标准**：新打一个 tag，Release 正文**只出现一份** changelog（内容来自 CHANGELOG），
且三平台共 8 个资产齐全。

### P0-2. 没有 tag 与 `version.json` 的一致性校验

**现象**：打 tag 时若忘记先 bump 版本，CI 不会拦住，
会产出「tag 名与包内版本号不一致」的发布。

**证据**
- `grep -rn "version.json" .github/workflows/*.yml scripts/*.sh scripts/*.py`
  除 `bump_version.py` 自身外**无命中** → CI 从未读取过 `version.json`。
- 对照：`pyproject.toml:10` 有 `requires-python`，
  说明项目有「声明 + 校验」意识，但发布链路上缺了这一环。

**影响**：错误产物会被签名、上传、分发；tag 一旦推送很难干净撤回。

**建议动作**：在 `test.yml` 增加一步（tag 触发时生效）：

```
- name: tag 与 version.json 一致性
  if: startsWith(github.ref, 'refs/tags/v')
  run: |
    v=$(python -c "import json;print(json.load(open('version.json'))['version'])")
    [ "v$v" = "${GITHUB_REF_NAME}" ] || { echo "tag ${GITHUB_REF_NAME} != v$v"; exit 1; }
```

**验收标准**：故意打一个 `v9.9.9` tag，Test workflow 失败并指出不一致。

### P0-3. 缺少运行时 Python 版本守卫

**现象**：用 Python 3.9 运行会以**与代码无关**的方式失败，误导排查方向。

**证据**
- 同一份代码实测：
  - `/usr/bin/python3`（3.9.6）→ `Ran 933 tests ... FAILED (failures=1, errors=1, skipped=2)`
  - `python@3.11`（3.11.16）→ `OK (skipped=2)`
- `pyproject.toml:10` 已声明 `requires-python = ">=3.11"`，
  但 `grep -rn "version_info" core/ scan.py` **无命中** → 运行时没有检查。
- 该声明只对 pip 安装生效；源码直跑（`python3 scan.py`）毫无保护。

**影响**：本会话真实发生，并一度导致误判根因。

**建议动作**：在 `scan.py` 与 `scripts/` 入口各加早退检查，
版本不符时打印可操作提示（当前版本、要求版本、建议命令）后 `exit 2`。

**验收标准**：`/usr/bin/python3 scan.py --help` 输出明确版本提示而非回溯。

### P0-4. 三处模块级 `Path.home()` 常量 —— 「改了要重启」类问题的共同根源

**现象**：技能库根路径在 `import` 时被求值成模块常量，运行期无法改变。

**证据**
- `core/skill_market.py:120` `_AGENTS_DIR = Path.home() / ".agents"`
- `core/skill_market.py:122` `_SKILLS_DIR = Path.home() / ".skills-manager" / "skills"`
- `core/skill_merge_advisor.py:21`、`core/skill_market_ops.py:26` 同一模式。

**影响**：这是**同一类缺陷**的根源，且本项目已因此出过 bug：
- 「技能市场源只在首次打开时探测，环境变化后无法刷新」属于这一族；
- `v0.23.0` 修的测试问题（用例读死开发机技能库）是同一根因的另一表现。

**建议动作**：改为访问器函数（`def skills_dir() -> Path`），
或抽出 `core/paths.py` 提供可注入 / 可重载的路径解析；
确需缓存时用显式 `lru_cache` 并提供 `clear()`。

**验收标准**：存在测试能在**不重启进程**的前提下把技能库根切到临时目录。

### P0-5. `test_stdio_probe` 有一次未定位的偶发失败

**现象**：全量跑时该用例偶发报 `stdio handshake timed out`，无法复现。

**证据**
- 一次全量跑中出现：
  `FAIL: test_handshake_and_tool_names ... AssertionError: False is not true : stdio handshake timed out`
  （当时 4 次全量跑中 1 次）。
- 此后复跑 **18 轮**（3 轮全量 + 15 轮专项）**再未复现**。
- 正常握手耗时 0.034–0.057s，预算 5.0s（约 100× 余量）；
  10 路 CPU 满载下该文件仍 0.102s 通过 → 不是纯负载问题。
- **注意**：它不是 CI 失败的原因（真实 CI 日志显示失败在 `test_skill_market_cli`）。

**建议动作**：不急着调超时，先让它**可诊断**：
- 失败时输出子进程实际耗时、stderr 内容、握手在哪一步超时；
- 给 `probe_stdio` 的 stderr 增加「超时时回读已缓冲内容」以便取证。

**验收标准**：下次偶发时，日志足以判定是调度停摆、管道阻塞还是子进程未启动。

### P0-6. 「禁止未经允许推 GitHub」的门禁 hook **不随仓库生效**（新增）

**现象**：门禁只存在于本机 `.git/hooks/pre-push`，**不在版本控制里**，换机器或重新 clone 后自动消失。

**证据**
- `git config --get core.hooksPath` → **未设置**（输出为空）。
- `.git/hooks/pre-push` 与 `scripts/git-hooks/pre-push` 内容一致，说明是**手工拷贝**进 `.git/hooks/` 的。
- hook 自身注释即承认：「本 hook 安装在 `.git/hooks/pre-push`，**不随仓库提交**」。
- 全仓 grep 未见任何安装脚本或 `core.hooksPath` 说明（`CONTRIBUTING.md`、`README.md`、`scripts/*.sh` 均无）。
- 该 hook 是**唯一**拦截 GitHub 推送的机制（拦截文案即「按当前约定，只有在你明确要求时才允许提交 GitHub」）。

**影响**：这是一条**安全/流程约定的单点失效**。
任何一次新克隆、换机、或 `.git` 目录重建，门禁都会静默消失，
而使用者不会收到任何提示——直到某次误推发生。

**建议动作**（二选一，前者更好）：
- **A**：把 hook 目录纳入仓库并由 git 自身加载：
  `git config core.hooksPath scripts/git-hooks`
  （该配置可写入一个 `scripts/install-hooks.sh`，并在 `CONTRIBUTING.md` 说明；
  注意 `core.hooksPath` 本身在 `.git/config` 里，仍需一次安装——但只需一条命令，且可脚本化。）
- **B**：在 CI 侧补一道防线：`test.yml` 中检查「非显式放行时不得出现推送到 github remote 的 workflow 步骤」
  （治本程度弱，因为 CI 拦不住本地误推，但可作为兜底）。

**验收标准**：新克隆仓库后，按文档执行一条命令即可让门禁生效；
或存在 CI 兜底检查且有对应测试。

### P1-10. `pyproject.toml` 宣告了测试依赖组与覆盖率配置，但 CI **完全不用**（新增）

**现象**：项目在打包元数据里声明了 pytest / coverage 及其配置，
但 CI 既不安装它们，也从不运行覆盖率——声明与实际行为脱节。

**证据**
- `pyproject.toml:19-22` 有 `[project.optional-dependencies] test = ["pytest>=8.0", "coverage>=7.0"]`。
- 同文件 `:27-44` 有完整的 `[tool.pytest.ini_options]`（`testpaths`/`python_files`/`addopts`）
  与 `[tool.coverage.run]`（`source = ["core", "scan"]`、`branch = true`）、
  `[tool.coverage.report]`（`exclude_lines`）。
- 但 `.github/workflows/test.yml:32` 实际只装 `PyYAML certifi`；
  `grep -c coverage .github/workflows/*.yml` 在**四个** workflow 里计数均为 **0**。
- 这与 P1-8 的文档矛盾同源：配置层设想用 pytest + 覆盖率，执行层用的是 unittest 且无覆盖率。

**影响**：维护者可能以为在跑覆盖率，实际从未产生过覆盖率数据；
也让「该装什么」在不同文档间说法不一。

**建议动作**（二选一，需明确）：
- **A**：让声明落地 —— CI 改用 `pip install -e '.[test]'`，
  并以 `coverage run -m pytest` + `coverage report` 产出报告（可选是否设门禁阈值）。
- **B**：删掉 `[test]` 组与 pytest/coverage 配置，全项目统一 unittest，
  并在 `pyproject.toml` 注释说明「测试用标准库 unittest，不引入 pytest」。

**验收标准**：`README`/`CONTRIBUTING`/`pyproject` 三者对「怎么跑测试」说法一致。

### P1-11. 无任何 Python 静态检查 / 格式化配置（新增）

**现象**：51 个领域模块 + 74 个测试文件（约 14000 行测试代码），
没有任何 lint、格式化或 import 排序工具的配置。

**证据**
- 以下文件**均不存在**：`.ruff.toml`、`ruff.toml`、`.pre-commit-config.yaml`、
  `.editorconfig`、`setup.cfg`、`tox.ini`。
- `pyproject.toml` 中 grep `ruff|black|isort` 无命中。
- 全仓 grep `pre-commit` 无命中（`pyproject.toml` 与所有 workflow 均未引用）。

**影响**：代码风格与 import 顺序完全依赖人工自觉；
新增贡献者无从得知约定；也无法在 CI 上自动拦住低级问题。

**建议动作**：引入 **ruff**（单工具即可覆盖 lint + format + import 排序），
配置写入 `pyproject.toml`，并新增一个 CI job；
首次启用建议先 `ruff check --fix` 全量清理一次，再设为门禁。

## P2 — 可以优化

### P2-12. GUI 是 6315 行单文件 HTML，改一行需重建 + 重装

**证据**：`gui/dashboard.html` 共 6315 行
（内联 `<script>` 约 4672 行、`<style>` 约 1441 行、185 个 `function` 定义）；
`frontendDist` 指向 `../gui`，HTML 被 brotli 内嵌进 Rust 二进制

### P2-15. 测试输出的裸 stderr 噪音

**证据**：全量跑汇总里混着负例用例的输出，例如
`❌ --all-profiles 与 --profile 互斥`、`❌ 扫描失败: boom`、`❌ profile 'bad' 加载失败`。

**影响**：这些是**预期内**的负例输出，直通终端后容易让人误判「是不是有失败」。

**建议动作**：负例用例把子进程 stderr 收进断言（而非直通），
或统一由测试框架捕获、仅在 verbose 模式显示。

### P2-16. 四个模块超过 600 行，职责边界需要复核（新增）

**证据**（`wc -l core/*.py`）
- `core/mcp_fixer.py` **900**
- `core/mainstream_registry.py` **782**
- `core/workspace_cleaner.py` **698**
- `core/config_store.py` **658**

（对照：全目录 51 个模块合计 14496 行。）

**影响**：单个模块承载多种职责时，改动牵连面大、测试定位困难。
其中 `mcp_fixer` 与 `workspace_cleaner` 涉及**写操作**，
按 `CONTRIBUTING.md` 要求必须遵循「备份 → 原子写 → 校验 → 回滚」安全链——
模块越大，越难保证每条写路径都完整走完该链。

**建议动作**：先做**只读复核**（不改行为），逐个确认是否混装了多种职责；
确认后按职责拆分，并保持对外接口不变。**不要在无测试保护下直接拆。**

**验收标准**：拆分为多个模块后，现有测试全绿且对外导入路径不变。
