界面规范（Skill MCP Studio 管理台）

本文件是 gui/dashboard.html 的唯一设计依据。所有页面与弹窗都必须遵守； 新增界面时先在这里找现成组件，找不到再补，并把补的那条写回来。

9 章节 22 检查项 3 个门禁文件 来源 docs/DESIGN.md

0设计判断（Design Read）#

定位

桌面端开发者工具管理台（dense product UI / admin panel）， 面向同时使用多个 AI Agent、需要统一管技能与 MCP 的开发者。

三档标尺（本项目取值，非通用默认）：

标尺取值理由
DESIGN_VARIANCE3 管理台要可预测。左右对齐、栅格稳定，不做非对称艺术排版。
MOTION_INTENSITY3 工具界面。只保留 hover / active / 展开收起的状态反馈，不做入场编排。
VISUAL_DENSITY6 数据密集但仍需呼吸感。信息分区块、留白分层，不排成电子表。

与 taste-skill 的关系：taste-skill 第 13 节把 dashboard / admin panel 列为 out of scope，并将此类界面指向 Fluent / Carbon / Polaris 等设计系统。本项目 不引入外部框架，沿用自身 token 体系；只采用 taste-skill 中与界面类型无关的 质量规则：颜色一致性锁、形状一致性锁、按钮与表单对比度、完整状态覆盖、 卡片克制、内容密度、禁用 em-dash。

2.2 列表行（.list-row）#

用于「多条同类条目 + 每行一个操作」的场景。这是市场、更新检查、技能列表的统一形态。

┌──────────────────────────────────────────────┐
│ 主标题（--text, --fs-base, mono 用于包名）      [操作] │
│ 元信息（--faint, --fs-xs）                            │
└──────────────────────────────────────────────┘
  • 行与行之间用 --line 分隔，不用每行一个卡片（卡片会撑高列表）。
  • 主标题可截断（text-overflow: ellipsis），完整值放 title 属性。
  • 操作按钮右对齐，纵向居中；同一列表内按钮文案一致。

只在需要表达「独立实体」时使用（技能卡、MCP 服务卡）。 不要用卡片堆一长串同类条目，那是列表行的职责。

场景卡片是各自独立的类，不是 .card 的修饰变体；新增卡片先看下表能否复用：

卡片类场景

.about-card关于页
.adv-card整理建议卡
.card通用容器（表格/区块外壳，--r-card + --shadow-card）

所有卡片共用同一套取值：底色 --panel、描边 --line、圆角 --r-card、内边距 --sp-7。

2.3b 卡片标签列对齐（.ac-path-row / .ac-meta-row）#

Agent 卡片里有两组「标签 + 值」行：路径区（APP / CLI / CONFIG）与 能力摘要区（Skills / MCP / Hook）。两组必须逐项同构，否则值区起点会差十几像素， 一眼看出错位（2026-10-12 用户截图反馈「最好保持对齐」）。

  • 行布局：两组同为 grid + grid-template-columns: 58px minmax(0, 1fr) + gap: var(--gap-4) + align-items: start。
  • 标签样式：同为 var(--mono) / var(--fs-2xs) / 字重 600 / text-transform: uppercase / var(--faint)；不加前缀圆点（装饰性状态点默认零）。
  • 分隔线：两组都不加竖线（单边 border-right 是错位感来源之一）。
  • 值区排版：容器 flex + nowrap，首个值 flex: 1 1 auto; min-width: 0，其余（状态标签）flex: 0 0 auto —— 状态标签恒贴右成一条竖线；路径列表改单列 grid 使路径等宽。 不用两栏 grid：Hook 行有 3 个子元素，第 3 个会被挤到第二行（渲染实测）。
  • 路径底色默认透明，:hover 才浮出胶囊：一张卡片近十个灰块会读成表单输入框。
  • 分隔线跨卡片对齐：卡片内有两条整宽分隔线 （能力区上沿、底栏上沿），两条都必须对齐。机制是锚定底部： .ac-meta 用 margin-top: auto 把 meta+foot 整块推到卡片底部， 于是线① y = 卡片底 − (meta 高 + foot 高)；.ac-foot 用 margin-top: 0 且不伸缩，线② y = 卡片底 − foot 高。两者都是自底向上的常量， 与路径条数无关 ⇒ 必然对齐。.ac-paths 保持 flex: 0 0 auto（不伸缩）。 走过的弯路：让路径区 flex: 1 1 auto 吸收差异，结果末行被裁进线里、线位仍漂移； 又曾去掉线①，用户明确「分隔线很重要」。代价：路径少的卡片在线①上方留一段空白。
  • 值胶囊与「未收录」空态必须度量一致：.ac-path-none 必须与 .ac-path-val 在决定行高的每个属性上相同（font-size / line-height / padding / border / font-family）。 实测不一致共 3px：空态少 1px 字号，且缺那条 border: 1px solid transparent （值胶囊为 hover 不抖动而留）。后果：分隔线用 margin-top:auto 锚定底部， 其前提是 meta 带高度恒定；矮 3px 会让整条线上移 3px、跨卡片错位，肉眼几乎看不出。 修好后实测 meta 高度恒为 109、两条线 Δ=0。
  • .ac-path-val.is-dim 只改颜色不改形状： color: var(--faint) + background: transparent + border-color: transparent。根因：它曾设 border-color: var(--line)， 而默认胶囊透明无边框，于是同一卡片里 Skills 成方框、MCP/Hook 是纯文本。 现规定淡化只表达「注册表默认值、非本机状态」，且三行在未安装时统一淡化。
  • 状态色语义：仅「全部写入」用 .tag.ok；部分写入用中性（绿色表示「已就绪」，8/21 不是）。
  • 未安装客户端：路径胶囊用淡化变体 .ac-path-val.is-dim （color: var(--faint) + background: transparent）—— 未安装时路径只是注册表「默认位置」，状态语义交给同行的「不适用」标签；仍可点击复制。 已安装时不得淡化。

不变量由 CardLabelColumnAlignmentTest 逐属性比对（列宽 / gap / 对齐 / 字体族 / 字号 / 字重 / 大小写 / 颜色）：只改一侧必然失败，要改就两边一起改，并同步 §2.9 的硬数字。

2.3c IDE / Agent 列表视图的列与图例（.agent-list-table）#

列表视图列序固定为：名称 | 类型 | 安装 | APP | CLI | CONFIG | 技能目录 | MCP | Hook | 操作。 每个状态列都必须配一条同名图例（.skill-legend），四态与列内取值一一对应： 两者都复用既有的 .skill-legend（.legend-label / .legend-item / .legend-swatch / .legend-note）。

2.3d 图例（.skill-legend）的放置与对齐#

位置：一律放在所说明内容的「上方」（2026-10-14 用户定案）。页面级图例涉及 Skills 页、IDE/Agent 页（MCP + Hook 两条）、MCP 页、一键合并预览弹窗，共 5 处。

走过一次弯路：曾把这 5 处全移到内容最下方（理由是「图例是读数据之后的对照说明」）， 用户看到实际渲染后判定「还是放在上面好看」，于是全部回退。教训：这类「放上还是放下」的取舍， 语义上两边都讲得通，必须看实际渲染再定。不变量由 LegendPlacementAndAlignmentTest.test_legends_come_before_their_content 钉住。

标签列必须定宽：.skill-legend .legend-label { min-width: calc(var(--sp-9) + var(--sp-3a)) }（31px）。 同一页会叠放多条图例，标签名字长短不一（MCP 3 字符 vs Hook 4 字符）， 不定宽时各自第一个色点错开 2px（实测）；定宽后严格对齐。与 §2.3b 的 58px 同一思路。

每条 .legend-swatch 都必须带语义 class：

class颜色 token用于
.ok--ok全部就绪
.warn--warn缺失 / 未配置
.err--err未设置 / 不可用
.na--faint不适用（未收录 / 仅审计 / 跳过）
.neutral--muted中间态（部分已配置）——既非就绪也非缺失

漏 class 是个隐蔽陷阱：<span class="legend-swatch"></span> 仍会命中基类拿到 9px 宽高，但没有 background 规则 → 渲染成看不见的占位； 同时零宽度的它会把后面的条目整体左移，造成同页两条图例错位（实测踩过）。 不变量由 LegendPlacementAndAlignmentTest 守住：色点必须有语义 class、各变体必须有 background、标签列必须定宽、图例必须排在内容之前。

Hook 列判据：只看有没有配置，不看配置内容（2026-10-13 用户要求）。某事件下只要存在任意 hook 条目即算「已配置」——命令内容、是否第三方工具，一概不参与判定；「缺关键事件」同理 = 该客户端支持 但完全没有配置的事件。此前只统计「命中特定工具命令签名」的事件，于是同一事件被别的工具占着时报「未配置」， 而客户端其实配了。

情形Hook 列显示说明
已登记且全部配置N/M（.tag.ok）N=已配置事件数，M=支持事件数
已登记且部分配置N/M（中性 .tag）绿色表示「已就绪」，部分配置不是就绪
已登记但未配置未配置（.tag.warn）
已登记但插件型（fix_supported=false）仅审计不支持模板注入
未登记 Hook 配置路径未收录（不是「不支持」）尚未收录其 Hook 配置路径

「未收录」与「不支持」必须分开：未登记只表示还没收录它的 Hook 配置路径，不等于 该客户端没有 Hook 能力。实测 22 个已安装客户端里只有 6 个登记了 hooks.clients， 一律显示「不支持」会对多数行过度断言。与 Hook 业务页 _hooksEntries 同口径。

分层作用域徽标 .al-scope：跟在状态标签后，形如 4 档， title 给出"分层作用域 N 档"；与 .al-metric 同族但更弱 （--faint 字色 + 虚线边框 + 透明底、不做 accent 高亮、不加 hover），因为它是元信息而非可点计数。

2.3e 技能表列（.skill-table，v0.31.0 增两列）#

七列：名称 / 分类 / 版本（st-ver，8%，mono，skill_meta.version， 无版本显示 -）/ 用途 / 更新（st-upd，9%，检查后三态 tag （技能行内只可能出现这三态；missing 的技能不在列表里）： 有更新 tag warn（title 含本地→远端版本）/ 最新 tag ok / 未知中性 tag， 未检查显示 -）/ 启用 / 操作。嵌套展开行 colspan="7"。更新数据来自 --market check（版本比对，只读），结果缓存于前端 SKILL_UPDATES。

检查结果四态（v0.31.1 用户实测缺陷修复）：outdated（有更新）/ current（已最新）/ unknown（无法检测）/ missing（登记失效）。前三态是「已装技能与上游的差异」； missing 是另一类事实：lock 里有登记、但统一库中已无该目录（装过又被删，登记残留）。 它必须单列，理由是原先把 missing 并入 outdated 会直接产出用户可见的矛盾： 技能列表按磁盘目录生成、画不出这一行（没有「有更新」tag），而「一键升级」取检查结果全量、 把它也算进去，于是列表说 2 个、弹框说 4 个。该态不提供「升级」动作 （无本地内容可覆盖，点了只会得到一条失败），文案用 .list-meta.is-err 承载。

计数口径纪律（v0.31.1）：任何「有多少个可升级」的呈现（工具栏 toast、 市场页汇总行、一键升级弹框标题与表格）必须同源，一律取 summary.outdated； 且 missing 单独报数、不混入前者。前端另有一道防线：一键升级只处理 SNAP.skills.skills 里真实存在的技能，被剔除的条目要 toast 说明原因， 不得静默少升。

检查结果第五态 repo_outdated（仓库待同步，v0.31.3）： missing 之外的另一类「此前查不到」的技能。本机实测 192 个技能里只有 39 个在 ~/.agents/.skill-lock.json 有来源登记，其余 153 个此前一律落进 unknown ——那个巨大的「无法检测」桶不是结论，是缺口：它们不属于任何「单技能来源」， 而是整仓库形态——统一库目录本身就是一个 git 工作区（origin 指向 my-agent-skills，分支 master）。这类技能的「上游」是该仓库的远端分支， 判定单位因此不是技能包 version，而是「本地 HEAD 与 origin/<branch> 之间，该技能目录有没有差异」。

判定实现 core/skill_repo_source.py（只读模块）：

项口径
适用条件paths.skills_dir() 是 git 工作区，且该技能不在 lock 登记里（有登记的技能仍走单技能来源，精确到各自上游仓库）
比对基准origin/<当前分支> 的本地 ref； 不发网络请求，由 --sync 或用户手动 fetch 更新
有更新判据git diff --name-only HEAD origin/<branch> 的路径收敛到技能目录后命中该技能
已有最新同一 diff 未命中该技能目录
本地有未提交修改unknown（同步必冲突，不能笼统报「可同步」）
判不成的任何一种unknown + 原因（git 缺失 / 非工作区 / detached HEAD / 缺上游 ref / 子命令非 0），绝不静默算 current

三条纪律：只读（只跑 rev-parse / diff / status / log，绝不 pull、fetch、checkout）； 不发网络请求（基准提交时间随 note 与 remote_time 透出， 否则「很久没 fetch」会被读成「远端没变」，那是把查不成当成没问题）； 路径收敛只认已知技能目录（仓库根的 README.md、LICENSE、 _core、_trash 不是技能，若不收口会凭空多出「待同步」条目—— 与 v0.31.1「列表 2 个、弹框 4 个」同一类矛盾）。

为什么必须是独立状态而不是并进 outdated：两者的升级通道 完全不同。outdated 走市场升级（npx 重装单技能）， repo_outdated 只能同步整个仓库；若并成一个状态，「一键升级」会拿 npx 去重装 一个仓库形态的技能并得到一条假失败，而且「可升级 N」与技能列表又会开始对不上。因此： repo_outdated 单独计数（summary.repo_outdated），不进 summary.outdated、不进「可升级」筛选段，市场页与技能表都不提供 「升级」按钮（技能表远端列显示 tag warn 的「待同步」，不可点击；市场页显示 「仓库待同步」）。汇总行与 toast 各自单独报这个数，措辞用「仓库待同步」，与「登记失效」区分开。

2.3f 技能启用状态（启停矩阵，N / M 徽标与三段筛选）#

「启用」不是技能自带的属性。上游 Agent Skills 规范里 SKILL.md 的 frontmatter 只有 name / description（外加可选 version 等）， 没有 enabled 字段；本项目 ~/.skills-manager/config.yaml 也没有启停开关。共享库里的技能「存在即存在」。所谓启用 = 某个客户端的 skills 目录里 有没有指向共享库该技能的符号链接。因此它是「每客户端 × 每技能」的矩阵， 允许「在 Cursor 启用、在 VS Code 未启用」这种状态。

三态判定（core/skill_state.py，ADR-17 审计的第 5 层）：

态判据
enabled 客户端 skills 目录里有指向本仓库该技能的有效符号链接； root 形态客户端（整个 skills 目录就是一条指向共享库的链接）则仓库内全部技能都算启用
disabled 技能在仓库里，但该客户端没有有效链接（真实目录里缺这条链接，或客户端目录不存在）
not_in_repo 技能名不在共享仓库 —— 这类技能不进入 skill_states， 界面上既不显示「已启用」也不显示「未启用」

三段筛选（data-seg）的口径必须与 N / M 徽标同源：

分段判据含义
on 已启用N === M && M > 0全部客户端都挂了
partial 部分启用0 < N < M挂了一部分
off 未启用N === 0一端都没挂

N = 该技能在 clients_states 里 states[skill] === "enabled" 的客户端数；M = clients_states 长度（= 图例要说明的「客户端总数」）。 徽标三色：N === M → .tag.ok、0 < N < M → .tag.warn、N === 0 → .tag.err。

图例文案必须写全两个字母：N / M = 已挂载该技能的客户端数 / 客户端总数 （共 M 个 IDE 与 Agent）。只写 N/M 会让用户以为 M 是技能总数（曾如此误解）， 图例就是为此存在。

为什么本机常年是「已启用 190 / 部分启用 0 / 未启用 0」（2026-10-24 实测）： 本机客户端多为 root 形态（~/.claude/skills 本身就是指向共享库的 符号链接），共享库里有什么就自动全开，根本没有逐个启用的余地。要让另外两段有 内容，必须先把客户端迁到 per-skill 形态（--migrate-skill-links）。这不是界面 bug， 是形态决定的。

写操作与只读查询：--enable-skill <skill> [--client X] / --disable-skill，实际动作是建 / 删那条 per-skill 符号链接 （core/skill_toggle.py）；root 形态返回 skip （「enable whole repo instead of per-skill」），mixed 形态返回 skip（须先迁移）。 只读查询用 --list-skill-states 打整张矩阵。

与「登记失效」（missing）的区别（务必分清）： missing 是 lock 有登记、磁盘没有目录（安装残留，见 2.3e），它连 not_in_repo 都不算 —— 根本不进技能列表，也不进启停矩阵； disabled 则是技能实实在在在仓库里，只是这个客户端没挂。 两者在界面上都表现为「看不到它生效」，但一个是数据残缺， 一个是正常配置状态，不可混为一谈。

空说明「为什么空」以及「怎么让它不空」，不留白屏
错误就地显示原因，不弹窗、不吞掉（仅限数据区自身状态）

  • 能力校验（2026-10-12 变更）：写入前按该客户端 events 过滤， 只写它认的事件。此前「勾了就一定写得上」（用兜底命令硬写），会把 Cursor 独有的 BeforeTabFileRead 写进根本不认识它的 Claude Code。现在跳过并回报 skipped —— 这不是「静默漏写」：GUI 只在客户端详情里列出它支持的事件。
  • 未配置（键不存在）与空列表语义不同：前者回落 template， 后者是明确的停用选择，不得回落。
  • 条目形态按客户端声明（entry_style），两套不可混用： Cursor 是扁平 {type, command, matcher}；Claude Code / TRAE / Codex / WorkBuddy 是嵌套 {matcher, hooks: [{type, command}]}。
  • 「缺关键事件」审计由写入意图推导（settings.hook_events ∩ 能力， 或回落 template 键），不是由能力全集推导 —— 否则 Claude Code 会把 29 个「支持但本次没打算写」的事件全报成缺失（假警报）。
  • 只增不减：客户端已有的非 ai-memory hook 必须原样保留。

2.11 概览页「全量检查」区（4 维度 + 端点，v0.30.0）#

概览页的「全量检查」按钮跑与托盘后台巡检同一条 --snapshot 命令（4 维度变更对比：IDE/Agent · MCP · Skill · Hook）+ 端点库整体探活 （--endpoint-status 无 --profile，不绑定活动端点）。 两处同源：概览页显示「检测到变更」⇔ 托盘红点（同一 has_changes 判据）。 2026-10-22 用户反馈：「首页的检查应该显示后台全量检查的内容，和状态栏的功能统一」。

  • 统一 UI（2026-10-22 用户反馈）：变更明细行内展开在该维度行内 （.note 小字，每条 name: detail），不设「变更详情」跳转链接； 4 维度与端点合并同一张 kv 表。
  • verdict 三态：全部连通（ok 绿）/ 部分不通（err 红）/ 全部不通（err 红）； 每端点行用 .tag.ok / .tag.err（有 CSS 定义，勿用幽灵类 endpoint-verdict）。
  • 单端点错误以 .note 缩在该端点行内（不弹页面级 banner——banner 只留给 执行失败，且新一轮检查开始时清除旧 banner）。
  • 状态覆盖：执行失败（error JSON 无 state）→ 红色「检查执行失败」+ 详情； 未检查 → 中性灰「尚未检查」。

3排版与间距#

  • 区块间距用 --gap-5(16) / --sp-8(20) / --sp-9(24) 三档，同一页面保持同一节奏。
  • 面板内边距：main 用 var(--sp-9) 28px 64px（上 24 / 左右 28 / 下 64）；卡片内边距 --sp-7(16px)；列表行内边距 --sp-4(10px) 14px。
  • 一行元信息里的分隔符最多一个，优先用换行或留白，不用符号堆砌。
  • 中文正文不手动加空格；中英文混排不加空格，靠字体回退处理。
  • 禁用 em-dash：正文、标题、标签、按钮文案一律用普通连字符或改写句子。

3b可访问性（硬要求，非可选）#

这几条由测试或明确的交互约束兜底，新界面必须满足。

要求做法为什么
键盘可达 交互元素保留 :focus-visible 外环（2px solid --accent，偏移 2px） 无鼠标用户需要知道焦点在哪
抑制 outline 必须给替代 若写了 outline: none，同一条规则里必须补 box-shadow 焦点态 否则键盘用户完全看不到焦点
尊重减少动效 所有 animation / transition 在 @media (prefers-reduced-motion: reduce) 里关闭 前庭敏感用户会因动效不适
触达目标 可点元素最小 32px 高（弹框内）/ 44px（移动端） 误触率
不靠颜色单独表意 状态同时有文字或形状（如变更卡的状态条 + 文字详情） 色盲可用
图标用 SVG 不用 emoji 当 UI 图标；统一 viewBox="0 0 24 24" 跨平台渲染一致
可点元素有指针 cursor: pointer 可发现性
已知例外

属于 §2.8 托盘弹框（不在管理台页面）：popover.html 的 .status-dot 呼吸动画是「显示的是缓存、正在刷新」的唯一视觉提示； 在 prefers-reduced-motion 下关闭动画，但 title 文案仍在，语义不丢失。

管理台页面不使用 .status-dot（0 处出现）；行内状态请用 §2.5 的 .dot 三态。

5检查清单（改完界面逐条过）#

取值与一致性

  • 颜色/字号/圆角/阴影全部取自 token，无字面值
  • 强调色只有一个
  • 圆角只用四档且用法一致（小徽标用 --r-hair）
  • 间距走 --gap-* / --sp-*（含扩展档），零字面值 （<style> 块与内联 style= 都算，由 NoLiteralSpacingTest 强制）
  • 按钮对比度达标，同一操作区一个 primary
  • 数字/包名用 mono，单位已中文化
  • 若动了 2.9 的硬数字，规范表与代码已同步

结构与状态

  • 同类条目用列表行，不是一长串卡片
  • 加载 / 空 / 错误三态齐备
  • 空态也要有信息量：不要出现「一排全 0」而无说明的界面
  • 无重复渲染（同一信息不在同屏出现两次）
  • 无 em-dash（正文、标题、标签、按钮文案）
  • 图标用 SVG（viewBox="0 0 24 24"），不用 emoji 当 UI 图标

交互与可达性

  • 可点元素有 cursor: pointer 与悬停反馈
  • 键盘焦点可见（:focus-visible），抑制 outline 处已补替代
  • 动效在 prefers-reduced-motion 下关闭
  • 状态不只靠颜色表达
  • 弹层能自然关闭（失焦收起 / Esc）
  • 弹层内动作按钮 min-height: 32px（触达目标）

主题与验证

  • 深浅两套主题都过一遍
  • 跑 python3 -m unittest tests.test_design_spec tests.test_dashboard_design_tokens tests.test_design_spec_contract
  • 若新增组件或变体，已回写本文件对应章节

附：双轨强制机制#

层载体有效力
