# 自定义模型体检（dsh-plugin-model-guard）

**一句话简介**：每次 DeepSeek Harness 启动时，体检 `@deepseek-ai/dsh-llm-pi-ai` 里手工声明的所有自定义模型——补齐图片输入标签、把上下文窗口拉到已知最大值，并在当前模型不识图时自动改由多模态模型转述图片；发现问题先报告，用户同意后才修复。

本插件是 **host-only bundle**：只在 Harness 宿主进程内运行，没有任何客户端 UI 组件、页面或设置面板。

---

## 它检查什么

对每一条路由下每一个手工声明的自定义模型（不是路由自带的内置模型），逐项检查下面四件事。

### 1. 图片输入标签

每个模型都必须在 `llm-pi-ai` 的配置里声明 `input: [text, image]`，Harness 界面才会接受给这个模型粘贴图片。缺少 `image` 标签会被报告（`IMAGE_TAG_OFF`），并可在用户同意后自动补齐为 `['text', 'image']`。

注意：这个标签只负责「让界面愿意把图片交出去」，**不代表模型真的能看图**——真正的能力由第 2 条单独判定。

### 2. 识图回退（运行时）

运行时插件监听 `agent/pre-step` 瀑布事件，在每一步真正送给模型之前判断：

- 这一步要用的模型**确实**是多模态：图片原样交给它，不做任何替换。
- 不是多模态：先从同一份自定义模型清单里挑一个真正支持多模态的模型，让它逐张描述用户粘贴的图片，然后把该步骤消息里的图片块替换成这些描述文本，再让当前模型继续完成这一步。

「真正多模态」的结论只来自三种来源，**绝不只看配置里的声明标签**（理由见第 1 条）：

- 探测：`probeImages: auto` 时，对每个还没有结论的模型发一次极小的红色 PNG 请求，按回答判断；
- 人工钉住：配置里的 `imageModels` / `textModels` 直接指定能力；
- 发现元数据：provider 的模型清单里声明的输入模态。

### 3. 上下文窗口

每个模型的**有效**上下文窗口必须等于已知的最大值：

- provider 自己的 `/models` 清单里声明了上下文窗口时，以它为准；
- 没有声明时，用 Harness 的默认值 `262144`（即未声明上下文窗口时的官方回退值）。

配置里写了更小的值 → 提升到最大值；如果发现结果**明确**给出一个更小的上限，则把声明值下调到该上限（模型实际只能到那里）。路由级的默认上下文窗口若低于 `262144` 也会一并报告。

### 4. 启动报告 + 用户同意

- 发现问题时，结论以一段紧凑的系统提示词段落呈现（`announce: true` 时），要求 agent 用中文向用户解释这些问题，并询问是否修复。
- `model_guard` 工具的 `status` 动作输出只读报告，`apply` 动作执行修复。
- `/model-guard` 命令让人直接触发同样的报告 / 修复流程。
- **插件永远不会在未经用户同意的情况下修改配置。**

修复结果通过 Harness 的 `configEditor` 服务持久化，不手写 profile 文件。

## 安装

用 `plugin_manager` 工具的 `install_bundle` 动作，`target` 指向本包的绝对路径：

```json
{ "action": "install_bundle", "target": "/Users/oswaldhill/personal/skill-mcp-studio/dsh-plugin-model-guard" }
```

安装后由包的 `cordis.patch.yml` 注入 bundle 配置行（已启用 `auditOnStartup` 与 `probeImages: auto`），此后每次进程启动都会自动体检一次。运行时要求 Node.js >= 20，纯 ESM，无第三方运行时依赖。

bundle 配置行形如：

```yaml
- insert:
    - id: model-guard
      name: dsh-plugin-model-guard
      config:
        auditOnStartup: true
        probeImages: auto
```

其余键按需追加到 `config` 下即可（见下一节）。

## 配置

| 键 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `enabled` | boolean | `true` | 总开关。设为 `false` 时插件完全不介入：不体检、不注入提示词段落、不改写图片消息（用于临时停用而不卸载）。 |
| `auditOnStartup` | boolean | `true` | 进程启动时是否自动执行体检。关闭后仍可用 `/model-guard` 或 `model_guard` 工具手动触发。 |
| `probeImages` | `'auto'` \| `'never'` | `'auto'` | `auto`：对还没有能力结论的模型各发一次极小的红色 PNG 请求来判定真实能力；`never`：完全跳过探测，只依据 `imageModels` / `textModels` 与发现元数据判断。 |
| `probeTimeoutMs` | number | `20000` | 单个模型能力探测请求的超时（毫秒）。推理模型在探测时可能思考十几秒，过短会把它们误判成「能力未知」。 |
| `discoveryTimeoutMs` | number | `8000` | 拉取 provider `/models` 清单（上下文窗口、模态等）的超时（毫秒）。 |
| `describeTimeoutMs` | number | `120000` | 让多模态模型描述一张图片的超时（毫秒）。实测一张普通界面截图需要 30 秒以上，过短会让回退直接失败。 |
| `describeMaxTokens` | number | `2048` | 单张图片描述允许的最大输出 token 数。宽幅长文本截图需要较大预算；触顶时转述末尾会明确标注「可能被截断」。 |
| `describerModel` | string | `''` | 指定用哪个模型做图片转述；留空则自动选择清单里第一个真正多模态的模型。 |
| `imageModels` | string[] | `[]` | 人工钉住为「能看图」的模型 id 列表，优先于探测结果。 |
| `textModels` | string[] | `[]` | 人工钉住为「纯文本」的模型 id 列表，优先级最高。 |
| `announce` | boolean | `true` | 是否把体检发现的问题作为紧凑的系统提示词段落交给 agent（由它用中文解释并询问是否修复）；设为 `false` 时只保留日志与命令 / 工具报告。 |
| `describePrompt` | string | `''` | 自定义图片转述用的提示词；留空使用插件内置提示词。 |
| `manageVisionPlugin` | boolean | `false` | 预留开关：是否由本插件接管第三方 vision 插件的配置管理；默认 `false`，即不改动第三方插件的配置。 |

## 工作原理

### 读取：`llm-pi-ai` 的 `providers` 配置

插件直接读取 `@deepseek-ai/dsh-llm-pi-ai` 插件行里的 `providers` 配置，枚举每条路由下所有手工声明的自定义模型。体检针对的是「手写声明的模型」，不是路由背后 provider 的全部模型。

### 判定：探测 / 钉住 / 发现元数据

- `probeImages: auto`（默认）时，对每个还没有能力结论的模型发一次极小请求：从 6 张**随机 4 位数字**图片里抽一张，要求它读出数字，按回答归类为 `image` / `text` / `unknown`；超时、鉴权失败等不产生结论，记为 `unknown`，不会误判成「不能看图」。
  - 数字（而非颜色）让「瞎猜」的概率降到万分之一；必须答对**这一张**的数字才算看见。
  - 判定会给足 512 token，并且**同时读正文和推理内容**（`reasoning_content` / `thinking`）：推理模型常常把预算全花在思考上、正文为空，而它可能已在推理里说出了数字——早期版本只读正文，会把这类模型误判成 `unknown`，进而让本来能直接看图的模型每次都被转述。
  - 明确表示「看不到图片 / 没有图片」会归为 `text`，这类模型确实需要回退。
- `imageModels` / `textModels` 人工钉住优先级最高，适合端点按次计费、模型很多时关掉探测。
- provider 的 `/models` 清单提供上下文窗口与输入模态，是上下文窗口目标值的第一来源。

### 运行时：`agent/pre-step`

在每一步送交模型之前拦截，按上面第 2 条完成「判定 → 选描述模型 → 转述图片 → 替换图片块 → 放行」的流程；真正多模态的模型完全不受影响，图片原样进入请求。

### 调用：`llm.stream`

- 转述图片时，插件通过 Harness 的 `llm.stream` 服务向选定的多模态模型发起一次普通流式调用：`describePrompt`（或内置的中文描述提示词）加上该图片附件，取回纯文本描述，并按 `describeTimeoutMs` / `describeMaxTokens` 约束这次调用。
- 当前这一步的模型调用链不变：插件只在消息进入模型之前，把该步消息里的图片块替换成描述文本，然后照常发出。

### 写回：`configEditor`

用户确认修复后，插件通过 Harness 的 `configEditor` 服务写入 `llm-pi-ai` 的 `providers` 配置，不直接编辑 profile 文件。

## 与第三方 `dsh-plugin-vision` 的关系

- 第三方 `dsh-plugin-vision` 包提供的 `vision-bridge` 服务在**当前 Harness 构建中不会被消费**，所以本插件不依赖它，而是在插件模式内自己实现了上述识图回退。
- 第三方插件的 `vision` 工具仍然可以按需使用（传文件路径识图），互不干扰。
- 本插件不是它的替代品，也不调用 `vision-bridge`；如果两者同时安装，识图回退由本插件自己完成。

---

## 已知限制

- 被替换成描述的图片，描述文本写在持久的用户消息里：该消息的模型可见内容中**不保留缩略图**（附件本身仍然存着）。
- 在不同模型下进入历史记录的图片不会被重新转述；当真实 provider 拒收这些图片时，Harness 内置的图片卸载机制可能会把它们省略掉。
- 能力探测要为每个未钉住的模型付一次极小请求；端点按调用计费或模型很多时，建议显式钉住 `imageModels` / `textModels`（钉住后不再探测，启动体检瞬时完成）。
- 第三方 `dsh-plugin-vision` 的 `vision-bridge` 服务在本 Harness 构建中不可用，相关能力由本插件的插件模式实现。

## 本机验证记录

在开发机上以 `plugin_manager install_bundle` 装入 `desktop` profile 后实测：

- 首次体检（未修复）：`路由 pudding-home-api：9 个自定义模型，0 个已声明 image 标签，4 个实测支持图片，0 个纯文本，5 个能力未知；最大上下文 262144`，9 条 `IMAGE_TAG_OFF`（error）。
- 系统提示词段落按预期出现，要求 agent 用中文列出问题并询问「是否现在修复？」
- 用户确认后执行 `model_guard` 的 `apply`：9 个模型逐个写入 `input: [text, image]`，`重新检查后仍可自动修复的项：0 项`，配置即时生效、无需重启；`cordis.patch.yml` 的 diff 仅新增这 9 处 `input`。
- 复检：`9 个已声明 image 标签，3 个实测支持图片，0 个纯文本，6 个能力未知；汇总：error 0 项，warn 0 项，info 0 项`，系统提示词段落不再出现（无问题即无噪音）。
- 真实图片回退：会话里粘贴一张截图，当前模型 `deepseek-v4.1-flash-1017` 能力未知时，图片由 `deepseek-v4.1-flash` 转述成中文描述后进入上下文——需求 2(b) 在真实会话中跑通。据此发现并修掉三个缺陷：转述混入模型思考过程、700 token 上限截断长截图、截断无提示（现为 2048 并在触顶时标注）。
- 流式思维链泄漏二轮修复（真实会话再次发现）：第一版修复只覆盖「行首锚点」形状；你用 glm-5.3 实测的那次，模型连锚点行都没输出，描述直接以「截图，一张聊天……」开头，剥离仍然失败。随后把 6 个可看图模型全部流式跑了一遍，摸清这个网关的真实行为：**流式时思考过程以 `备注` 开头、以 ``` 围栏结束，整段塞进 content 增量**（`reasoning_content` 为空，非流式则分离干净）。据此把 `stripPreamble` 重写为四级规则：① 取**最后一个**行首锚点（思考可能提前起草锚点，但真描述永远在最后）；② 没有锚点时切到最后一个 ``` 围栏行；③ 跳过紧跟引号闭合符的引文锚点并取最后候选；④ 全都没有时丢弃开头的规划段落与「输出。」类过渡前缀。连续 3 次流式实测：全部干净以 `图片类型：` 开头、无思考残留、6/6 数字正确。新增 4 个测试对应四种真实泄漏形状（含代码截图内含围栏不得误切的用例）。
- 流式思维链泄漏（真实会话发现）：glm-5.3 走回退时，`deepseek-v4.1-flash` 的转述开头带出了整段思考（「我需要提取图中的文字内容……我准备按这个要求组织 / 输出。」）。根因有二：(a) 该端点在**流式**调用时把思维链直接混进 `content` 增量（`reasoning_content` 为空，非流式则不会）；(b) 旧的 `stripPreamble` 用 `indexOf` 找第一个锚点，而思考里**引用了提示词**（含「图片类型：」字样），切割点落进引文里。修复：锚点必须出现在**行首**才算数；没有行首锚点时，跳过紧跟引号闭合符的锚点并取最后一个候选。连续 3 次流式复测：全部以 `图片类型：` 开头、6/6 数字正确。
- 转述模型实测（同一张真实界面截图，用插件自带的描述提示词）：`deepseek-v4.1-flash` 平均 8.3 秒、`deepseek-v4.1-flash-1017` 4.7 秒、`qwen3.8-flash` 平均 29.2 秒、`qwen3.8-omni-flash` 35.6 秒、`qwen3.8-max` 38.5 秒；四者都能读对截图里的 6 个数字、都以 `图片类型：` 开头、都没有思维链残留。速度差 8 倍，因此 `describerModel` 从 `qwen3.8-flash` 改为 `deepseek-v4.1-flash`。
- 运行时视图：`model_guard` 的 status 会用 `llm.resolveModelInfo()` 回读当前默认模型，打印「运行时视图：provider/model → 上下文 N，输入 [text, image]」；并逐个回读同一路由下所有模型，把与配置声明不一致的地方列为 `RUNTIME_MISMATCH`。写入配置后若运行时视图仍显示旧值，说明 llm 适配器没有重建，配置文件与生效值不一致——这是本次踩到的真实情形：源码变更（不只是配置）必须重装/重启才会重新 import。
- 上下文上限实测：给端点发一个约 500k token 的请求被接受（`prompt_tokens: 500033`），再加大到约 1M token 时报 `<400> Range of input length should be [1, 1000000]`——即该网关的输入上限是 **1,000,000 token**，而 Harness 无声明时的回退值是 262144。因此在该路由上写了 `defaultContextWindow: 1000000`（并把 `defaultMaxTokens` 显式设为 32768），9 个模型共用这一默认值，无需逐个声明。另测 `max_tokens` 上限：qwen/glm 系列为 131072，超出会被拒。
- 能力探测修正：早期判定只读正文且只给 24 token，推理模型（如 `deepseek-v4.1-flash-1017`、`kimi-k3`）把预算花在推理上、正文为空 → 被误判 `unknown`，导致它们本该直接看图却每次走转述。改为随机数字 + 512 token + 同时读推理内容后，9 个模型的结论稳定为 6 个可看图、3 个纯文本、0 个未知（再用「读数字 / 描述图片」两种问法交叉验证，结论一致），并已钉进 `imageModels` / `textModels`，启动体检不再探测。

## 验证方法

1. **命令**：在会话里执行 `/model-guard` 查看只读体检报告（每条路由的模型数、已声明 `image` 标签数、实测支持图片数、纯文本 / 能力未知数、最大上下文、逐条问题，以及选定的识图回退模型）；`/model-guard fix` 直接写入可修复项，修复即时生效、无需重启。
2. **工具**：让 agent 调用 `model_guard` 工具，`action: "status"` 返回同一份报告（附加 `refresh: true` 可忽略缓存、重新探测并读取端点模型清单），`action: "apply"` 在用户同意后执行修复并回报改动项。
3. **启动日志**：每次进程启动都会输出本次体检结论——全部通过时是一行「检查通过」，有问题时输出问题数量，以及每条问题的 `code` 与说明。
4. **系统提示词**：`announce: true`（默认）时，问题清单会以紧凑的系统提示词段落交给 agent，要求它用中文向你解释并询问是否修复；未获同意不会改动任何配置。
5. **复检**：修复后再次执行 `/model-guard`，应完全通过或只剩不可自动修复的项；`imageModels` 里钉住的模型在界面中应能直接接收粘贴的图片。
